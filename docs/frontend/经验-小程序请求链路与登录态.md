# 小程序请求链路与登录态 —— miaowu 经验适配（EWF 软件层 · frontend）

> 适用上下文：EWF frontend = uni-app（Vue3 + TS + Vite + Pinia），**仅构建微信小程序**（对应 epics AD-18 / Story S3.1）；backend 沿用 miaowu REST 骨架 —— Spring Boot `/api/v1` + `{code,message,data}` 信封（code=0 成功）+ 微信登录 openid/JWT → 单身份单设备（AD-16/AD-17，MVP 无绑定/迁移/多设备治理）；无文件上传、无 OBS/CDN、无多端 H5/App、无管理后台。

## 1. 统一请求封装（request<T>）

### miaowu 做法

`request.ts` 是全仓唯一 HTTP 出口，基于 `uni.request` 的 Promise 封装：

```ts
export async function request<T = unknown>(options: RequestOptions): Promise<ApiResponse<T>>
```

- **信封**：`ApiResponse<T> = { code: number; message: string; data: T }`，`code === 0`（`ErrorCode.SUCCESS`）为成功；业务失败返回 `body`，由调用方看 `code` 决定分支。
- **RequestOptions 关键档位**（带代码注释原义）：
  - `showError` —— “是否自动处理错误提示”（默认 true，出错统一 toast）；
  - `showLoading` / `loadingText` —— 需要时 `uni.showLoading({title, mask:true})`，收尾必 `hideLoading`；
  - `requireAuth` —— “是否需要认证（默认 true）”，本地判过期即刷新/失败即返回 UNAUTHORIZED；
  - `attachAuth` —— “非强制登录接口是否在本地有 token 时附带 Authorization”，默认等于 `requireAuth`（登录/公开接口置 `requireAuth:false` 即可）；
  - `baseUrl` —— 默认 `API_BASE_URL`，允许个别接口换底座（miaowu 上传走 `UPLOAD_BASE_URL`；**EWF 不需要**）。
- **鉴权头**：`headers['Authorization'] = 'Bearer ' + token`（仅当 attachAuth 且本地有 token）。
- **Content-Type**：默认 `application/json`；`timeout: 15000`。
- **HTTP 非 2xx**：`toast( normalizeToastErrorMessage(body?.message) || \`请求失败 (${statusCode})\` )`；401 单飞刷新（见 §2）；返回 `{ code: body?.code ?? statusCode*100, message: 该文案, data: null }`。
- **信封非 0**：`showError && toastMessage` 才 toast（文案也要过清洗）；直接 `return body`（不吞业务语义，让调用方处理）。
- **网络异常**：catch → `console.error('[Request] 请求异常:', url, err)`，toast「网络异常，请检查网络连接」，返回 `{ code: SERVER_ERROR, message: err.message, data: null }`。
- **数据归一** `normalizeRequestData`：`undefined/null` → 不带；`string/ArrayBuffer` 原样；`object` 直传；其余 `JSON.stringify`。
- **便捷方法**：`get/post/put/patch/del`。`get()` 把 params 拼 query string，自动丢弃 `undefined/null/''` 的键。
- `requestMessage.ts`：`normalizeToastErrorMessage` 先 `trim`，空串返回 `""`，**大小写不敏感地滤掉默认成功文案 `"success"`**，避免后端顺手返回的 `"success"` 被 toast 成一条白色提示。

### EWF 怎么用

- AD-16/18 已定 `{code,message,data}`（code=0）信封 + 单一 `VITE_API_BASE_URL` + 统一 `api/request`：**整体复制 request.ts 的鉴权/错误/加载骨架**，删掉 `uploadFile/uploadImage/getLocalFileMeta/UploadOptions` 及其 import（EWF 无上传）。`baseUrl` 退化为单一常量（可保留 `baseUrl?` 默认参数但只喂 `API_BASE_URL`）。
- 保留 `requireAuth / attachAuth` 两档语义：EWF 登录接口用 `{ requireAuth: false }`（无 token 也能打）；普通业务查询默认 true。
- 保留 `showError` 开关：登录失败等场景置 false，由页面自己 toast 更精确的文案。
- 保留 `normalizeToastErrorMessage`：EWF 后端只要有任何接口顺手回 `message:"success"`，就能省掉一条无效 toast。这是「便宜但体验相关」的细节，别丢。
- 页面**禁止散落 `uni.request`**（spine AD-18 也强调）——所有后端访问都经这一个函数，护栏（§8）才好锚定路径字面量。

## 2. HTTP 401 单飞刷新队列（并发只刷一次 + 刷新失败不永久挂起）

### miaowu 做法

模块级三个状态/函数：

```ts
let isRefreshing = false
/** 等待刷新完成的请求；入参为 null 表示刷新失败，必须结束等待避免永久挂起 */
let refreshSubscribers: Array<(token: string | null) => void> = []

function onTokenRefreshed(newToken: string): void { refreshSubscribers.forEach(cb => cb(newToken)); refreshSubscribers = [] }
/** 刷新失败时唤醒所有排队请求，否则并发请求会永远 await 卡住（例如 join 成功后回首页） */
function onTokenRefreshFailed(): void { const subs = refreshSubscribers; refreshSubscribers = []; subs.forEach(cb => cb(null)) }
```

- **触发点 A —— 发送前本地提前判过期**（见 §3）：`requireAuth && 本地 token 过期` 时进入单飞：首个请求置 `isRefreshing=true` → `refreshAccessToken()` → 成功 `onTokenRefreshed(newToken)`，失败 `onTokenRefreshFailed()` 并返回 `UNAUTHORIZED`；**并发请求不各自刷新**，而是 `await new Promise(resolve => subscribeTokenRefresh(resolve))`，刷新完成后拿新 token 续上。
- **触发点 B —— 收到 HTTP 401**：`if (!isRefreshing && requireAuth)` 才单飞刷新；成功则 `onTokenRefreshed` 后 **`return request<T>(options)` 用新 token 重试原请求一次**；若已在刷新中（他人接管）则走等待者分支。
- **刷新失败/无 refresh token/异常**：`clearTokens()` + `redirectToLogin()`（见 §4），向调用方返回 `{ code: UNAUTHORIZED, message: '登录已过期', data: null }`。
- `refreshAccessToken()`：读 refresh token → `POST ${API_BASE_URL}/auth/refresh`，body `JSON.stringify({ refreshToken })` → 成功 `body.code===SUCCESS && body.data` → `saveTokens(accessToken, refreshToken, expiresIn)` 并返回新 accessToken；否则清 token 跳登录返回 null。

### EWF 怎么用

- MVP 单作者 + JWT，过期刷新实际很少触发，但**并发 401 只刷一次** 与 **刷新失败必须 `cb(null)` 唤醒所有等待者** 是两个正确性不变量：若写成每个 401 各刷一次，会雪崩；若刷新失败不唤醒排队者，请求会**永久挂起**（原注释强调的教训）。原样保留这套「单飞 + 订阅者队列」。
- `onTokenRefreshFailed` 里那句“否则并发请求会永远 await 卡住”是真实事故后的补丁，移植时把三件套一起搬，不要只搬刷新成功路径。
- 刷新接口路径 `/auth/refresh`、登录接口 `/auth/login/wechat-mini` 属于 S0 `frontend-facing API 契约`，EWF 侧需后端按 miaowu WechatMiniClient/JWT 模式提供；若后端 MVP 先不做 refresh（仅长 token），则 request 层把“发送前刷新分支”去掉、保留 401 → `clearTokens + reLaunch 登录`，把刷新队列函数留空备后续。

## 3. 令牌本地提前 5 分钟判过期（storage.ts）

### miaowu 做法

`storage.ts` 用 `uni.setStorageSync/getStorageSync/removeStorageSync/clearStorageSync` 包一层类型安全存取（JSON 序列化，try/catch 吞读写在 storage 不可用时也不崩页面），并提供 Token 快捷方法：

- 键名常量带业务前缀（miaowu 用 `miaowu_`，集中在一个 `STORAGE_KEYS` 对象里，页面不裸写字符串）：
  `ACCESS_TOKEN / REFRESH_TOKEN / TOKEN_EXPIRE_TIME / USER_INFO / …`
- `saveTokens(accessToken, refreshToken, expiresIn)`：写 access/refresh，并把**过期时间戳持久化** `expireTime = Date.now() + expiresIn * 1000`（毫秒）。
- `isTokenExpired()`：

```ts
const expireTime = getStorage<number>(STORAGE_KEYS.TOKEN_EXPIRE_TIME)
if (!expireTime) return true
// 提前 5 分钟视为过期，触发刷新
return Date.now() >= expireTime - 5 * 60 * 1000
```

- `clearTokens()` 一次清三个 key。`USER_INFO` 单独持久化（登出时再移除）。

### EWF 怎么用

- 整份 storage 封装可复制；**key 前缀从 `miaowu_` 换成 `ewf_`**（便于开发者工具 storage 面板里一眼区分；小程序 storage 本来就按 appid 隔离）。
- 「提前 5 分钟判过期」价值 = 冷启动/发请求前先本地拦截，避免“必过期”的请求白跑一趟再等 401 往返刷新。EWF 单设备单作者仍适用：`expiresIn` 通常很短（如 2h），本地持久化过期戳能让 `app.js/onLaunch` 直接决定“要刷新还是先拉 me”。
- `USER_INFO` 缓存：EWF 可只缓存 `{nickname, deviceId?}` 最小集，**本地缓存永远不是权威**（spine AD-2：客户端状态不作权威数据），登录/首页仍以 `/auth/me` 或登录响应为准。

## 4. 登录态失效 UX（uni.reLaunch + 当前页判重 + 平台条件编译）

### miaowu 做法

`redirectToLogin()`（request.ts 内）：

```ts
function redirectToLogin(): void {
  const pages = getCurrentPages()
  const currentPage = pages[pages.length - 1]
  if (currentPage?.route === 'pages/login/index') return   // 已在登录页则不再重复跳

  uni.reLaunch({ url: '/pages/login/index' })
  uni.showToast({ title: '请重新登录', icon: 'none' })
}
```

- 用 **`uni.reLaunch`** 而不是 `navigateTo`：reLaunch 关掉整条页面栈再开登录页，避免“登录页叠在死页栈上”导致返回键回不去；toast 提示“请重新登录”。
- **判重**：取 `getCurrentPages()` 栈顶 route，若已是登录页就直接 return —— 防止“刷新失败→reLaunch 登录→登录中又 401→再 reLaunch”的重复跳转/闪烁。
- 登录页内部按端条件编译区分：

```html
<!-- #ifdef MP-WEIXIN -->
  实际 uni.login → store 登录逻辑
<!-- #endif -->
<!-- #ifndef MP-WEIXIN -->
  uni.showToast({ title: '请在微信小程序中使用', icon: 'none' })   // H5/App 占位
<!-- #endif -->
```

- 登录成功后的去向用 `uni.switchTab`（tab 页）或 `uni.reLaunch`（非 tab），并支持「扫码邀请/redirect 白名单」回跳（EWF 无此场景可删）。

### EWF 怎么用

- **reLaunch + 栈顶判重**是登录态失效 UX 的核心，EWF 原样保留；`currentPage?.route` 判重可避免连发 401 时反复跳登录。
- EWF **只保留 MP-WEIXIN 分支**：删掉 `#ifndef MP-WEIXIN` 整段（无 H5/App），页面里不再需要“请在微信小程序中使用”的占位；条件编译注释可整体去掉，代码更干净。
- reLaunch 目标路由以 S3.1 `pages.json` 为准：失效 → `/pages/login/index`；登录成功 → 直达设备主页（FR-F-001 “登录后直接进入唯一设备”，非 tab 用 `uni.reLaunch`，EWF 无多 tab 则无需 switchTab 分支）。
- 登出成功同样建议 `reLaunch` 到登录/首页，别 `navigateBack` 到已被清理的栈。

## 5. Pinia userStore（登录/登出即清 token + 持久化）

### miaowu 做法

`userStore.ts`（setup store）：

- **state**：`userInfo` 用 `getStorage(USER_INFO)` 做初始值（冷启动不白屏）；`loading`。
- **getter**：`isLoggedIn = computed(() => !!userInfo && !!getAccessToken())` —— **user + token 双条件**，只 cache 了 user 但 token 被清（过期/登出）不算登录。
- **登录 action**：`loginByWechatMini(data)` → `post('/auth/login/wechat-mini', data, { requireAuth: false })`；成功（`code===0 && data`）→ `saveTokens(access, refresh, expiresIn)` + `userInfo.value = res.data.userInfo` + `setStorage(USER_INFO, …)` → true；finally 收 `loading`。
- **fetchUserInfo**：`get('/auth/me')` 成功回填 userInfo + 持久化。
- **logout**：清空页面相关 state → `clearTokens()` → `removeStorage(USER_INFO)` → `removeStorage(CURRENT_STAR_ID)`。
- **单一 `API_BASE_URL` 常量**：`constants.ts` 里 `API_BASE_URL = import.meta.env?.VITE_API_BASE_URL || 默认值`，整个前端只此一处拼后端地址。

### EWF 怎么用

- 只裁出一个最小 store：`userInfo`、`deviceId`（登录响应里后端返回的固定设备映射，MVP 单身份单设备）、`isLoggedIn`、`loginByWechatMini(code)`、`fetchUserInfo()`、`logout()`。miaowu 的 myStars/角色角标/权限待办/switchUser 等全部删除。
- **登出/登录失败必须成对清**：`clearTokens()` + `removeStorage(USER_INFO)` 一起做（忘了清 token 会导致 `isLoggedIn` 计算仍 true、401 又把它打回登录页的反复横跳）。miaowu 的 `logout()` 就是这个“原子清空”范式。
- `userInfo` 只作展示缓存，**权威在 backend**（登录响应 + `/auth/me`）。
- constants 只保留 `APP_NAME`、`API_BASE_URL`、`DEFAULT_PAGE_SIZE` 等 EWF 需要的；`UPLOAD_*`、`WX_APPID` 的 TODO 注释（miaowu 是 `//TODO：请填写微信小程序 AppID`）在 EWF 骨架里应填真实 appid，别留 TODO 上路。

## 6. 微信登录页（uni.login → store；协议勾选；头像昵称）

### miaowu 做法

- **取 code**：`#ifdef MP-WEIXIN` 内 `uni.login({ provider: 'weixin' })` → `loginResult.code` → `userStore.loginByWechatMini({ code })`。code 是 5 分钟一次性凭证，**后端拿 code 换 openid 再签 JWT**（miaowu WechatMiniClient/JWT 模式），小程序端不落 openid。
- **协议勾选是硬门槛**：`policyAgreed = ref(false)`，注释：“未默认勾选，需用户主动勾选后再登录 @wechat 收集用户隐私行为规范”。未勾选点登录 → toast 提示先去勾选《用户协议》《隐私政策》；协议链接是 `<text>` + `@tap.stop` 打开本地协议页。**不得做成“登录即默认同意”**。
- **头像昵称完善（EWF 可砍）**：登录成功若昵称是占位/无头像，弹 `profile-sheet`，用 `open-type="chooseAvatar"` + `<input type="nickname">` 收集微信头像昵称 → 先 `uploadFile`（OBS）再 `updateProfile`；另有“直接登录”用内置默认头像 + 随机名 `关注喵友XXXX`。整套依赖 OBS 上传 + 头像库。
- **去向**：登录成功按优先级 reLaunch —— 待激活邀请码 → redirect 白名单回跳 → 首页。

### EWF 怎么用

- 保留：`uni.login` → `loginByWechatMini({ code })` 直通后端；**协议勾选**（微信对收集用户隐私的强约束，EWF 若登记用户 openid 也需《用户协议》《隐私政策》，勾选后按钮才可用）。
- **可大幅简化**：EWF MVP 单作者（作者本人），**无头像库、昵称非必需** —— 砍掉 `profile-sheet` 的 `chooseAvatar/type=nickname/上传默认头像/updateProfile` 全套；登录成功后端直接返回/或复用微信昵称即可直达设备主页。
- 登录按钮 loading 防连点、失败 toast 用后端 `message`（经清洗）或通用「登录失败，请重试」，这两点照抄。
- 不需要「暂不登录去首页」的话可删（EWF 主页本身要登录才有意义，登录直达设备）；保留与否由 UX 稿定。

## 7. 合法域名与构建（manifest / project.config / 分包 2MB / 本地脚本）

### miaowu 做法

**构建与产物**
- `package.json` scripts：`dev:mp-weixin = uni -p mp-weixin`、`build:mp-weixin = uni build -p mp-weixin`、`type-check = vue-tsc --noEmit`、`analyze:mp-weixin = node ./scripts/analyze-mp-weixin-bundle.mjs`。
- 产物在 `dist/build/mp-weixin/`；`project.config.json` 设 `"miniprogramRoot": "dist/build/mp-weixin/"`，微信开发者工具**打开的是 dist 目录**，改源码后重新 `uni build`。
- `vite.config.ts`：`plugins:[uni()]`，alias `'@' -> src`；`manifest.json` 的 `mp-weixin.setting`：`urlCheck:false`（**仅开发工具**免校验域名）、`es6/enhance/postcss/minified:true`、`optimization.subPackages:true`。

**合法域名**
- 开发态：开发者工具可勾“不校验合法域名”或 `urlCheck:false`；**真机预览/体验版/发布必须**在微信公众平台「开发管理 → 服务器域名 → request 合法域名」配置 **HTTPS** 的 `API_BASE_URL` 域名。review-rubric 里也把这条显式列为 `[ASSUMPTION]`：个人主体小程序受类目与发布限制，作者本人自备域名/备案。

**分包控制 2MB**
- `pages.json`：主包只放 tab/启动相关页，其余业务页全部按业务域拆 `subPackages`（miaowu 的 `pages-sub/{cat,star,guardian,checkin-sub,ledger,share,mine,settings}`）。主包被微信限制在 2MB，分包让主包远离上限。
- `scripts/analyze-mp-weixin-bundle.mjs`：读 `dist/build/mp-weixin`，主包体积 = 总 - Σ分包，预算 `mainPackageBudgetKb = 1900`（给 2MB 上限留余量），超预算 `process.exitCode = 1`；打印各分包体积、Top 文件、以及 **pages-sub 里仍引用主包 `/static/` 根资源**的清单（提醒把大图挪 CDN 或分包 static）。README §5.5 还建议 `build.rollupOptions.splitChunks` 剥离 `request.ts` 等共享底座，避免多分包重复打包。
- `constants.ts` 里 base url 来自 `import.meta.env.VITE_API_BASE_URL`，本地联调由 `env-scripts/start-local-test-backend.sh` 生成 `frontend/.env.development.local`（gitignore）。

**本地进程脚本（诚实标注）**
- `env-scripts/start-local-test-frontend.sh` / `stop.sh`：通用范式 = `logs/*.pid` 记 PID + `stop_by_pid_file` + `pkill -f` + `lsof -tiTCP:PORT` 强杀端口、`.env.example` 以 `set -a` 加载、curl 轮询就绪。**注意出入**：已提交的 start 脚本实际启动的是 `frontend-web`（React 管理台，:4310），而 README §4.3 把它描述成 uni-app H5 dev —— 脚本与文档不一致（uni-app mp-weixin 的开发/调试闭环并不需要这个 HTTP server）。

### EWF 怎么用

- 工程脚本照抄最小集：`dev:mp-weixin` / `build:mp-weixin` / `type-check` / 一个 `analyze:mp-weixin`。产物目录 + `project.config.json.miniprogramRoot` 的「打开 dist」模式是 uni CLI 标准，EWF 不用 HBuilderX 也能跑。
- `manifest.json` **删掉 h5/app-plus/mp-alipay/mp-baidu/mp-toutiao/quickapp** 段，只留 `mp-weixin`；`setting.urlCheck:false` 仅开发工具；EWF 后端合法域名/备案照 review-rubric 建议写进 `[ASSUMPTION]`（作者自备）。
- **分包从骨架第一天就铺**：EWF 页面量小，仍建议把登录/主流程放主包，设置/记录等拆 1–2 个分包，配合 analyze 脚本守主包预算（把 `1900KB` 预算抄进来当 CI/本地门禁）。
- 真机微信联调只需：`uni build -p mp-weixin` → 开发者工具打开 dist → 预览；本地后端要能被真机访问时用隧道（cloudflared）或把域名加进 request 合法域名。`env-scripts` 的 stop/pid/lsof 范式可在 EWF 将来需要“一键起本地 backend + 打隧道 + 写 .env”时复用，但 **EWF 无需照搬 frontend-web 启动脚本**（那是被排除的管理后台）。

## 8. 真源护栏（technical-identifier-freeze.test.cjs 思路）

### miaowu 做法

`src/technical-identifier-freeze.test.cjs` —— 纯 Node `assert`（**不依赖 jest/vitest**，`node xxx.test.cjs` 即可跑），目的是**防“纯前端文案改名”漂移掉技术标识符**：

- 场景：UI 上「喵星记」前台改名，但**后端接口路径、动作枚举 key 必须冻结**；测试断言这些字面量仍存在。
- **锚定技巧（防假阴性/假阳性）**：
  - 数组真源用 `key: 'WATER'` 引号锚定 —— 裸 `includes('WATER')` 会被 `'WATER_RELEASE'` 之类更长串吞掉；map 真源用 `WATER:` 冒号锚定，同理防被 `WATER_RELEASE:` 吞；
  - 契约字段用 `field:` 锚定（`catId:` 不被 `catIds:` 满足），防单数字段被复数化时假绿；
  - **反向断言**：epic 文字里写错的关键词（`CHANGE_WATER`/`TNR_CAPTURE`）**必须不出现**，防止实现者“照着文档改代码”把对的 key 改错。
- 读取真源用 `readSource(relPath)` 先 `assert.ok(fs.existsSync)`（防路径改名后测试变空转）。
- 每条断言带可读的 message（`AC-x: <文件> 应包含…`），全绿打印一行 `全部断言通过`。

### EWF 怎么用

- 把思路剪裁成 **EWF 少量断言**，同样 `src/*.test.cjs` + `node` 直跑：
  1. 请求底座/常量真源里必须仍含 `{code,message,data}` 信封字段与 `code` 成功判 0 的关键字面量（防止有人把信封拍平成别的结构）；
  2. storage 键前缀 `ewf_`、`STORAGE_KEYS.ACCESS_TOKEN/REFRESH_TOKEN/TOKEN_EXPIRE_TIME` 键名不漂移；
  3. S0 冻结的 frontend-facing 接口路径字面量（如 `'/auth/login/wechat-mini'`、`'/auth/refresh'`）与请求层引用一致；
  4. （S0 契约落定后）同步相关字段名（如 `scripture_version`、`round_id`、`command_revision`）若在小程序端出现，用 `field:` 冒号锚定冻结。
- 沿用三个原则：**按文件/语义定位真源**（不硬编码下标）、**带界定符锚定而非裸子串**、**文案可改但技术标识符冻结**。UI 改字是家常便饭，这类护栏几行 assert 就能防住“顺手把接口也改了”或“照着错误文档把对的 key 改坏”。

## 9. EWF 边界与排除表

| 能力/模块 | miaowu 形态 | EWF 处置 | 理由 |
| --- | --- | --- | --- |
| H5 / App / Harmony / mp-alipay / mp-baidu / mp-toutiao | manifest 多端段 + `#ifndef MP-WEIXIN` 占位 + h5 devServer | **不迁** | AD-18：仅微信小程序 |
| `frontend-web`（React 管理后台）及 env-scripts 里指向它的启动脚本 | 独立 Vite 工程 | **不迁** | EWF 无后台 |
| OBS 直传 / 上传（`uploadFile`、`/upload/image/policy|complete`、`UPLOAD_BASE_URL`、`UploadScene`、`types/upload.ts`、OBS/CDN 公网域名） | 头像/凭证直传 | **不迁** | EWF 无文件上传；去上传则 **request.ts 删除整段 upload**，本文也不保留 policy/OBS 说明 |
| 头像昵称完善弹窗（`chooseAvatar`/`type=nickname`/默认头像上传/`updateProfile`） | 登录后引导 | **简化** | 单作者、无头像库、昵称非必需；后端可直接用微信昵称 |
| 手机号登录 / 绑定手机号 / getPhoneNumber | `loginByPhone`、`bindWechatPhone` | **不迁** | MVP 微信 openid 单身份即可 |
| 多角色/喵星/成员/邀请码/打卡防刷/账本/订阅支付/角色角标 | userStore 大而全 | **不迁** | 单身份单设备；store 只留 §5 最小集 |
| 公众号直达/运营常量（`OFFICIAL_ACCOUNT_*`）、扫码邀请 join、`switchUser` 调试 | utils/constants + store | **不迁** | EWF 无公众号运营/邀请/多账号调试 |
| `utils/uni-error.ts` isUserCancelError | 上传/扫码取消判定 | **按需** | EWF 无上传；若将来有长按/录音等取消场景再取用 |
| 分页/列表契约类型（`PageData/PageResponse/PageParams`） | types/api.ts | **按需** | EWF 若有“记录列表”可用；MVP 直连设备状态可不需要 |
| 请求封装 / 信封 / Bearer / 两档鉴权 | request.ts 核心 | **沿用** | §1 |
| 401 单飞刷新 + 失败唤醒队列 | request.ts 模块级 | **沿用** | §2 |
| 令牌提前 5 分钟判过期 + storage 封装 | storage.ts | **沿用**（前缀 `ewf_`） | §3 |
| 登录态失效 reLaunch + 栈顶判重 | request.ts `redirectToLogin` | **沿用** | §4 |
| 最小 userStore + 成对清除 | userStore.ts | **沿用裁剪** | §5 |
| 微信登录 code 直通 + 协议勾选 | login/index.vue | **沿用**（去多端/头像） | §6 |
| 合法域名 urlCheck / mp-weixin 构建 / dist 打开 / analyze 分包护栏 | manifest/project.config/scripts | **沿用** | §7 |
| node-assert 真源护栏 | src/*.test.cjs | **沿用裁剪** | §8 |

> 一句话收束：**EWF 从小程序请求链路里要继承的是「一个统一出口 + 信封语义 + 单飞刷新不挂死 + 令牌提前过期 + reLaunch 判重 + 成对清除 + 协议勾选 + 分包与真源护栏」这套骨架，把一切“多人/多端/上传/运营”能力留给排除表。**
