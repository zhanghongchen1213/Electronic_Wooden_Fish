# PRD Quality Review — 电子木鱼（2026-09-08 二层组织版）

## Overall verdict

这份 PRD 的骨架是扎实的：产品愿景紧贴“一敲一字”闭环、非目标与 MVP 边界诚实、addendum 把决策反转与验证门禁单独归档，二层组织（嵌入式层 / 软件层）在概念上成立且 FR-E/B/F 编号保持稳定可追踪。真正的风险集中在 Done-ness 的不对称——§6 软件层 19 条 FR（FR-B-001…009、FR-F-001…010）没有任何验收准则，而 §5 嵌入式 FR 普遍带“验收”；同时“95% / 1 秒”实时性指标在 SM-3、FR-E-008、FR-F-003 三处以不可对账的落点各写了一遍。这两点不会动摇产品方向，但会让下游故事拆分与 backend/frontend 工程在“done 是什么”上各自猜测。

## Decision-readiness — adequate

决策大多以“决策”而非“考虑项”出现：§2 明确“BLE/Wi‑Fi 可作为 ESP32-S3 的硬件能力保留，但不进入 MVP 产品链路”、§8 非目标给出硬边界、addendum §2 用“撤销…”句式记录每一处反转（含默认音量 50、二层重组、Air780EGP 专属 GPIO 重映射），并附理由。SM-C1（§10）是真正的反指标，点名“不以同时常开 BLE/Wi‑Fi/4G、堆叠音效或增加功能数量换取在线感”。对单人原型而言，这种透明程度高于一般 PRD。

弱点是全文没有一个显式的 Open Questions / 残余风险段：工程上最不确定的几件事——PVDF 误触发率、1 秒 20 次输入可靠性、Air780EGP 发射峰值是否掉压、全天续航——被放在 §11 与 addendum §6 的“去验证”清单里，但清单没有写“若某项失败，MVP 范围如何裁剪”。

### Findings

- **medium** 无风险→范围影响映射（§11、addendum §6）——工程未知项以“待核验”清单呈现，但没有说明核验失败后的降级路径（例如 20/s 输入达不到、4G 峰值掉压时是砍在线链路退回本地，还是换模组）。*Fix:* 把“工程验证入口”扩成一张 residual-risk 表，每行给失败后果与对应裁剪选项，让这些项仍是“可决策的边界”而非“隐藏的范围炸弹”。

## Substance over theater — strong

没有 persona 堆砌——唯一用户就是 Hongchenke，UJ 全由具名主角承载。没有创新 theater——产品不宣称新颖，复用边界在 addendum §5 用“可复用 / 不可照搬”逐项划清。NFR 与成功指标高度产品化：SM-1/2/4/5 都对应可复现的行为，SM-C1 是真正的权衡指标；未出现“可扩展、高可用”式样板句。Vision（§1）不可换皮：实体敲击、7 字带、离线记录、微信确认动画是这台设备独有的闭环描述。

## Strategic coherence — strong

全篇有一个统一论点：物理动作 → 设备即时反馈与本地记录 → 4G 高水位同步 → backend 权威游标 → 小程序确认呈现 → 历史积累，形成“创作者愿意持续使用”的回路。FR、UJ、SM 都落在这条主线上，没有悬空能力；单《心经》、单设备、单 backend 的范围类型与该论点匹配。SM-1/2/3/4/5 分别验证回路的各段，SM-C1 作为反指标存在。

### Findings

- **low** SM-6“创作者完成原型后愿意持续使用”（§10）是承载整个论点的指标，却只能数周后回看，工程期内不可测。*Fix:* 补一个工程期内可测的代理指标（如样机就位后连续 N 天自发完成一轮或日均使用回升），或把 SM-6 显式标为 post-MVP 回看项，避免它在一段时间里既不可证伪也不可推进。

## Done-ness clarity — thin

§5 嵌入式 FR 普遍带“验收”，且多数可操作（重启恢复、充电不计数、7 字带不丢字、音量跨重启保留）。但软件层整段失守，且验收语言里夹着多处无数值量词，这是本 PRD 对下游最脆弱的维度。

### Findings

- **high** 软件层 19 条 FR 全部无验收准则（§6.1 FR-B-001…009、§6.2 FR-F-001…010）——每条只有一段义务描述，与 §5 嵌入式“验收：”行形成鲜明不对称。backend 幂等、frontend 回放这类最能出 bug 的逻辑，PRD 层没有给出任何“可判定 done”的条件。*Fix:* 为每条软件 FR 补可验证条件，至少覆盖不变量：重复提交同高水位不增计数（B-002）、只按差量推进一次游标（B-003）、版本不一致即停并报配置错误（B-004）、断线重连只补未展示差量且不跳字不重字（F-004/F-009）、待确认不提前声称完成（F-005）。
- **high** “95% / 1 秒”口径三处不可对账（§10 SM-3“95% 有效敲击在 1 秒内被小程序展示”、§5.8 FR-E-008 验收“95% 事件 1 秒内被 backend 接收并可推送”、§6.2.3 FR-F-003“稳定网络目标为 95% 事件 1 秒内更新”）——同一数字落在链路三段的不同点；若每段都按 1 秒设计则串行相加不可能，若意图是端到端则 FR-E-008 的落点又太早。*Fix:* 定义唯一的端到端目标（敲击 → 小程序渲染）并给出分段预算，让 SM 与相关 FR 引用同一口径。
- **medium** 硬件验收的模糊量词无测量界——FR-E-002“携带、取放和普通环境振动不会大量误触发”、FR-E-003“1 秒 20 次无明显漏记或重记”、FR-E-005“不会叠加成不可辨识噪声”、SM-1“不出现明显漏记、重记或乱序”。样机验证时“明显/大量”无法让工程师签字。*Fix:* 换成数值界（如连续 3×20 次零丢失、误触发低于 N 次/日、限速合并在固定窗内至多 k 声）或明确“以创作者演示签收、原型阶段不设统计门槛”。
- **medium** FR-E-009（状态与低打扰反馈，§5.9）与 FR-E-010（USB-Serial-JTAG，§5.10）没有验收，而 E-001…008 都有——E-009 尤其是一句“通过 CW2015、RGB、AMOLED 和音频表达…状态”，整条无可验证后果。*Fix:* 为两者补验收（E-009 至少落到“各状态可被对应通道辨识并可在样机上演示”；E-010 落到“上电可识别 USB CDC、烧录不依赖 CH340X”），或将 E-009 并回 E-006/E-007 的可验证子项。

## Scope honesty — adequate

§8 非目标具体且真（BLE/Wi‑Fi、GPS 业务、自动 OTA、多设备、迁移、公开账号、社交、排行榜、提醒、付费、多平台前端、量产认证、云运维），§9 用包含/不包含双向锁定 MVP，addendum §2 把所有 de-scope 写成显式“撤销”，addendum §7 甚至要求新反转追加到 `.memlog.md` 而非删除旧行——这是教科书级的诚实。

缺口在于本 PRD 没有任何内联 `[ASSUMPTION]` 标签，也没有 Assumptions Index。对单人原型这多半可接受，但有几处推断值得落一句。

### Findings

- **low** 微信小程序运行形态的假设未标注——FR-F-001“登录后直接进入唯一设备”依赖后端有合法 HTTPS + request 域名（真机预览需在小程序后台配白名单），且个人主体小程序受类目与发布限制。作者本人具备 uni-app 能力大概率自明，但这类环境依赖若不写成 `[ASSUMPTION]`，后续他人或数月后的作者会把它当已解决项。*Fix:* 在 §6.2 前加一行 `[ASSUMPTION: 小程序以开发者/体验版形态供唯一作者使用，后端域名与备案可由作者自备]`。

## Downstream usability — adequate

正向很干净：FR-E/B/F 编号连续、唯一、无旧版残留；每个 UJ 都有具名主角 Hongchenke 且直接驱动对应 FR；addendum §4 给出到 architecture.md、docs/{embedded,backend,frontend,contracts} 的索引；§7 明确把同步契约细节外置到 `docs/contracts/sync-contract.md`，不重复定义。§2 与 addendum §1/§2 对“二层组织、前缀保留”的口径一致，编号不重排，epics/architecture 引用不会被重构打断。

短板集中在软件层 FR 的可抽取性——它们没有验收，故事拆分必须从义务句里自己推断测试条件（见 Done-ness high-1）；另有少数术语闭合问题。

### Findings

- **low** §7 同步合同字段表与 §4 术语表不闭合——`scripture_version`、`battery_percent`、`network_mode`、`audio_config_version`、`firmware_version` 出现在 §7（及 FR-B-004/FR-E-004 的 `scripture_version`），却没有词条；FR-B-004 让 `scripture_version` 承担“版本不一致即停”的语义，读者却要到 sync-contract.md 才可能找到定义。*Fix:* 术语表补 3–5 个字段词条，或加一句“§7 字段语义以 sync-contract.md 为准，本文不重复定义”的显式声明。

## Shape fit — adequate

两层顶层组织在概念上成立：嵌入式层与软件层（backend + frontend 同属非设备的“云端/连接软件”）符合“设备 ↔ backend 同步契约”这条真实接缝；backend 与 frontend 共享同一数据模型与权威关系，放在一个伞下合理。FR-E/B/F 前缀保留意味着重组没有破坏编号稳定性，addendum §2 明确声明“不重排、不更名，仅重组归属章节”，下游引用安全。对个人原型的复杂度，这个组织度不算 over-formalized，且 §5 硬件、§6 软件的分章确实利于分层阅读。

两点保留：其一，伞下 backend/frontend 仍各自成节、各自编号，FR 前缀本为三叉——所以这是“在三叉之上加了一把伞”，导航层级没有真正减少；其二，两条低严重度的不贴切（见下）。

### Findings

- **low** 没有“软件层横切 FR”的家庭——所有软件 FR 都归 B 或 F，SM-3 的端到端实时性（device → backend → frontend）没有任何 FR 承接，属于“两层都有、两层都不拥有”。*Fix:* 明确承认伞下仍按 B/F 三叉推进即可；若后续出现 backend+frontend 共同义务，再引入 `FR-S-*` 前缀，不必现在为它设空位。
- **low** UJ-4“完成《心经》并开始新轮次”（§3.5）更像 UJ-1 的终局/分支场景而非独立旅程（单用户原型的四条 UJ 略微过密）——它不是 theater，每条都驱动需求，但粒度可再校准。*Fix:* 把 UJ-4 标为 UJ-1 的完成态分支，或在 §3 附一句 UJ 与运行场景（在线/离线/触摸/完成）的映射表。

## Mechanical notes

- FR-E-001…010、FR-B-001…009、FR-F-001…010 连续、唯一，无旧版残留；UJ-1…4 均有具名主角。
- 编号稳定：addendum §2 与 §2 主文对“二层重组、前缀保留、不重排”口径一致，本次重构未破坏追踪链（正向）。
- 术语闭合问题：§7 五个同步字段未进 §4 术语表（见 Downstream usability low-1）。
- §7“统一状态”存在类别混排：`待设备应用` 是命令下发状态，与 `本地已记录/同步中/已同步/待同步/同步失败` 这类累计同步状态并列；术语表已把它区分开，建议 §7 加一句“待设备应用属命令通道状态，不与累计同步状态并列”。
- `[ASSUMPTION]`、`[NOTE FOR PM]`、Open Questions 全篇 0 处，无 Assumptions Index——对单人原型可接受，但 BSP 复用（addendum §5）、4G/SIM 可用性、微信域名三个推断值得做内联标注。
- 与旧版 review 的差异：本版评估的是重组后的二层结构；旧版对“三模中间态”的若干措辞（如三模网络优先级、SM-C1～C2）已随 BLE/Wi‑Fi/4G 去三模化而过期，不复用。
