# 对抗式构造评审 — Electronic_Wooden_Fish ARCHITECTURE-SPINE

## 评审方法与判据

透镜：为每一对将要由不同下游单元（bmad-spec / epic / story / build）独立实现的「下一级单元」假定其实现者逐字照抄 spine 中每一条 AD，再构造它们在运行时相遇的场景。只有当冲突**不是**由某条 AD 文字本身排除、而是落在 AD 之间的缝隙里时，才算真洞。

判据：共享数据结构不一致 / 同一实体两个 owner / 状态变更路径相悖 / 边界含糊。

结论先行：spine 的 AD 体系在「单点权威」上写得非常强（AD-1/2/9/16），但**权威的「推进方 / 确认方 / 只读方」三者关系没有闭环**——尤其是跨重启、跨离线、跨断线的状态量（经文轮次、日统计、命令生效、展示水位）只写了「谁拥有」，没写「谁推进、谁确认、靠哪个协议字段收敛」。以下是 4 个可构造的洞 + Deferred 复核。

---

## 发散对 1 — 设备本地经文状态机（完成→重启） × backend `round_cursor` 权威

**两个单元**：Embedded「经文推进/完成锁定服务」（消费 AD-1、AD-9、AD-15）与 backend「游标/完成权威」（消费 AD-2、AD-3）。

**各自照 AD 都能自洽的读法**

- AD-2：backend 拥有 `round_cursor`/`round_state`/完成锁定的唯一权威。
- AD-1：设备输入进入**同一个**有效敲击队列，「共享本地累计、**经文推进、完成锁定**」；「完成遮罩中直接忽略输入」。
- AD-15：设备本地持久化 `round_state`/`round_cursor`，断电重启后可离线续敲。
- AD-3：同步上传「累计高水位」；backend 返回 `acked_total`、差量、待应用命令——**响应字段里没有 `round_state`/`round_cursor`**（L74-75、L262）。

**构造场景（都合规，却冲突）**

1. 经文长度 N（心经固定字符数）。设备 `acked_total`=199、`round_cursor`=199、round 1 中，随后离线。
2. 用户离线敲到 260，正好跨过一轮边界。设备**本地**必然要即时推进经文显示，于是本地 `round_state=completed`、`round_cursor=260`、完成遮罩锁定输入（AD-1 语义）；`local_total=260`。
3. 恢复联网，设备上报 `local_total=260` 与本地 `round_state/cursor`。backend 侧 delta=61，从自己的 acked=199 推进到 260——恰好撞上轮次边界。
4. 现在 backend 实现者面临两个都符合 AD-2 的选择：(a) 用 `acked_total % N` 自行推进，得出 `round_state=round2`、`cursor=0`（认为已完成并自动开启下一轮）；(b) 信任设备上报的 `round_state=completed`、`cursor=260`，停在「完成待重启」。
5. 设备侧的完成遮罩靠什么解除？若设备等 backend「重启指令」，而 AD-3 的同步响应**不回传 round_state/cursor**，设备永远等不到、永远遮罩；若设备在「从头开始」点击时本地重启到 round2 cursor=0 并继续累计，而 backend 选了 (a) 之外的 (b) 停在 completed，则下一轮敲击累计再次跨边界时 backend 的 delta 推演与设备的轮次计数**永久错位**。

**spine 为什么拦不住**：AD-2 只写了「backend 拥有权威」，AD-1 只写了「设备本地共享推进/完成锁」，AD-15 只写了「设备持久化游标」——「谁推进、谁确认、设备本地未 ACK 的完成能否被用户重启、backend 是否自动重启轮次、用哪个协议字段收敛」全都没写。同步响应字段清单（AD-3、L262、L219）里恰恰缺 `round_state`/`round_cursor` 的**回传**，于是两个状态机的收敛通道不存在。

**AD 建议（一句话）**：新增 AD——`round_state`/`round_cursor` 只由设备本地推进（敲击/完成/从头开始均即时本地生效并可持久化），backend 不做独立推进或自动重启轮次、只按累计差量与经文长度做边界一致性校验后持久化，**且同步响应必须回传 backend 确认后的 round_state/round_cursor** 作为设备校准基准，并明文允许「本地完成未 ACK 时用户可经『从头开始』本地重启下一轮、随高水位一并上报」。

## 发散对 2 — 设备端「今日」显示单元 × backend 日统计归档单元

**两个单元**：Embedded「今日/待校时/同步状态」展示（消费 AD-2、AD-6、AD-9）与 backend「日统计切分归档」（消费 AD-6、AD-16）。

**各自照 AD 都能自洽的读法**

- AD-6：日统计由 backend 按「其配置时区、以接收/确认时间归档离线增量」；设备不保存绝对敲击时间；设备在硬断电后、取得可信时间前显示「待校时」。
- AD-2：设备屏幕只能呈现 backend 已确认进度，本地待同步数据必须以「同步中/待同步」标记。
- AD-3：同步响应只回 `acked_total`、差量、待应用命令、可信时间——**不含当日已确认统计**（L75、L262）。

**构造场景**

1. 设备在校时后要显示「今日」——它没有绝对敲击时间（AD-6），唯一的本地选择是维护一个「自本地日界以来」的累计桶，日界用取得的可信时间换算。但 AD-6 未规定可信时间以哪个时区下发、backend 配置的时区是多少。
2. 设备实现者用网络时间（多半是 UTC）切本地日界；backend 实现者按 Asia/Shanghai 切归档日界。每日 00:00–08:00 CST 窗口，设备「今日」与 backend「今日」对同一批敲击归属不同天。
3. 更基本的：设备在 23:50 同步过、累计 10 次，随后离线。跨过设备本地日界后用户敲 100 次，设备「今日」显示 100。凌晨 00:30 补传，backend 按**接收时刻**把这 110 次全部归档进「今天」。设备本地「今日=100（离线累计）」与 backend「今日=110」永久不一致——而 spine 没有任何一条 AD 规定设备「今日」与 backend「今日」的收敛关系，也没有字段能让设备拿到 backend 当日统计来校准。

**spine 为什么拦不住**：「今日」这个实体有两个 owner——设备本地日桶（为满足 AD-2/AD-9 的即时展示）与 backend 归档日统计（AD-6）。AD-6 只规定了 backend 侧的切分 owner，**没规定设备侧「今日」是非权威、日界时区必须与 backend 同一、以及离线/当日未同步时必须以「待同步」标记并不得与 backend 数字混同**。信任时间时区与 backend 配置时区的一致性也无契约。

**AD 建议（一句话）**：收紧 AD-6——正式「今日/日统计」唯一属于 backend 且日界=backend 固定配置时区、归档时刻=接收/确认时刻；设备端「今日」是非正式本地展示，日界须按与 backend 同一时区换算，凡当日存在未同步累计差值即带「待同步」标记，**同步响应应回传 backend 当日已确认计数**供设备校准，禁止设备维护与 backend 无校准关系的第二套日统计。

## 发散对 3 — backend→frontend 差量推送模块 × frontend 断线回放/补齐模块

**两个单元**：backend「推送已确认差量」（消费 AD-17、AD-2、AD-3）与 frontend「回放/补齐」（消费 AD-17、AD-18）。

**各自照 AD 都能自洽的读法**

- AD-17：frontend「只按 backend 确认顺序逐字呈现一次」「恢复时先按 backend 差量顺序回放、回放期间新事件排队、结束后无缝接入实时」「断线经查询接口补齐、**只补未展示差量**」。
- AD-17 文本自述「backend→frontend 实时通道选型待定（WebSocket 或轮询，见 Deferred），无论选型均须满足本 AD 的增量与去重语义」（L163、L51）。

**构造场景（WS 被选定时）**

1. frontend 已展示到 `acked_total=100`，其「已展示水位」记在本地。连接断开。
2. 断线期间 backend 确认了 101..120。frontend 重连：照 AD-17 同时做两件事——发查询补齐「未展示差量」，并重开 WS 接入实时。
3. backend 推送模块若按「每连接记忆游标」恢复，新连接无从记忆旧游标，合理实现是**在连接建立瞬间取当前 acked 作起点**；查询接口则**在请求处理瞬间取快照**。二者各取各的快照：若查询快照在 t0=115 冻结，WS 连接在 t0 之后建立、起点取到 120，则 116..120 既不在查询结果里、也不会从 WS 推来（起点已过）——**永久空洞**。
4. 反向竞态则造成重复：查询返回 101..120，同时 WS 又从 115 推起，115..120 重放两次。AD-17 说「只补未展示差量」，但「未展示」的基准是 frontend 自己的本地水位还是 backend 的连接游标？两种实现都自认合规，谁也无法判断对方的水位。

**spine 为什么拦不住**：AD-17 写了三条语义（顺序、去重、补齐）却**没有定义「未展示差量」的唯一计算方与收敛基准**（服务端单调序号？查询快照冻结点？frontend 已展示水位？），也没有要求实时消息携带可判重的单调序号。顺序语义 + 快照与推送竞态 = 一快一慢两个实现必然错位。

**AD 建议（一句话）**：收紧 AD-17——断线恢复以「backend 在查询请求内冻结的权威快照水位 S」为唯一补齐基准，实时通道每条消息必须携带 backend 统一分配的单调序号且 frontend 只消费 >S 的消息，按序号判重并在发现跳号时先查询补齐再续播；禁止「backend 按连接记忆游标恢复推送」与「frontend 自算未展示差量」两种机制并存。

## 发散对 4 — backend 命令状态机（待设备应用→已生效） × 设备命令应用/回 ACK 调度

**两个单元**：backend「命令存储与生效翻转」（消费 AD-5）与 Embedded「命令应用 + 活动窗口调度」（消费 AD-3、AD-5、AD-14）。

**各自照 AD 都能自洽的读法**

- AD-5：命令携带单调 `command_revision`；backend 只保留下发最新修订；**收到设备 ACK 后才呈现为「已生效」**，否则 frontend 显示「待设备应用」。
- AD-3 + AD-14：同步在「敲击/设置触发的活动窗口」内进行，**无持久连接**；上报后回低功耗（AD-14）。
- AD-15/同步字段：设备本地持久化 `command_revision`（L219 字段清单含 `command_revision`），但 AD 未规定它是「设备已应用修订」还是「待 ACK 的目标修订」。

**构造场景**

1. backend 下发 `command_revision=6`（亮度 20%），设备在线窗口内应用成功。
2. 设备按 AD-5 应「回 ACK」——但 ACK 只能搭在**下一次**活动窗口（无持久连接）。用户敲完这一阵后不再敲击、也不再设置，活动窗口永不开启 → ACK 永远发不出。
3. backend 保持「待设备应用」，frontend 镜像设置页永久显示「待设备应用」，而设备**早已实际应用**——两个单元的「已生效」判定依据不同（backend 靠 ACK 事件，设备靠本地应用动作），中间没有任何「已应用修订高水位」的持续上报通道来收敛。
4. 若实现者把 `command_revision` 解读为「待 ACK 的目标修订」（一次性 ACK 语义），丢一个 ACK 就永久错；若解读为「设备已应用修订的高水位」（每次同步都携带），backend 才能靠「已应用 ≥ 下发的修订」翻转。spine 字段清单一个词两种读法。

**spine 为什么拦不住**：AD-5 把「生效翻转」绑死在单次 ACK 事件上，却与 AD-3/AD-14 的「活动窗口由用户触发、无持久连接」组合时没有兜底——ACK 不是可靠送达的。既没规定设备在任意后续窗口持续携带「已应用 command_revision」高水位，也没规定 backend 对同一/更高已应用修订的幂等不翻转。

**AD 建议（一句话）**：收紧 AD-5——`command_revision` 在同步包中语义固定为「设备已应用修订的单调高水位」并在每次活动窗口都携带；backend 收到「已应用 ≥ 下发修订」即幂等翻转为已生效，不依赖单次 ACK 送达；frontend 提供可触发的「立即同步」作为离线命令 ACK 的兜底通道。

## Deferred 复核——哪些项其实会让两个单元发散，不该延后

| Deferred 项 | 与哪个发散对耦合 | 为何延后会致发散 |
| --- | --- | --- |
| A-2 JSON 文件布局与原子写（schema 下沉 docs/contracts 后再冻结；.memlog L20 确认 spine 不冻结 schema） | 发散对 2 的 backend 侧；发散对 1 的「同步响应字段」也押在 sync-contract 冻结上 | 「同步确认模块（推进 acked_total，写单状态 JSON）」与「日统计归档模块（写日统计文件）」两个 backend 单元若在 schema 冻结前各自实现，「双文件非原子、先写哪个」无契约：先归档后推进且中途崩溃 → 重传同一高水位会**二次归档**（日统计重复）；先推进后归档且崩溃 → 日统计丢一批。这不是实现细节，是跨文件顺序/幂等语义，应在两模块 spec 前收敛。发散对 1 需要同步响应回传 round_state/cursor，同样依赖 sync-contract 冻结。 |
| A-1 backend→frontend 实时通道选型 | 发散对 3 | spine L51/L163/Deferred 仍写「待定（WebSocket 或轮询）」而 .memlog L19 已记录「保留 WebSocket」——文档自相矛盾，推送模块与回放模块会照两份不同现实 spec。更本质地，AD-17「无论选型语义不变」只在引入服务端单调序号/快照基准后才成立（见发散对 3）；选型悬空期让两模块各自照 AD-17 落地必然一快一慢。**A-1 不该延后到两模块 spec 之后**；即便选型继续悬空，也应先把与选型无关的「单调序号 + 查询快照为唯一补齐基准」写进 AD-17。 |

次要提示（非发散对）：Deferred「音频高速合并阈值 / 活动窗口时长」作为表现参数延后是安全的——活动窗口**时长**是调参，但「窗口开始/结束边界 = 落盘与命令 ACK 的原子点」这一**结构语义**（发散对 1、4 都依赖）不应随调参延后，应在 sync-contract 中固定。

## 汇总

| # | 两个下一级单元 | 缝隙类型 | 一句话 AD 建议 |
| --- | --- | --- | --- |
| 1 | 设备本地经文/完成状态机 × backend round_cursor 权威 | 同一实体两个 owner + 状态变更路径相悖 | 游标只由设备推进，backend 只校验确认；同步响应回传 round_state/cursor；明文允许未 ACK 完成的本地重启 |
| 2 | 设备端「今日」× backend 日统计 | 同一实体两个 owner + 边界含糊（日界/时区） | 正式今日唯一在 backend 且时区固定；设备今日非权威、带待同步标记；响应回传当日已确认计数 |
| 3 | backend 差量推送 × frontend 断线回放补齐 | 共享数据结构/水位基准不一致 + 次序竞态 | 补齐基准=查询快照水位 S；实时消息带单调序号；两种水位机制禁止并存 |
| 4 | backend 命令生效翻转 × 设备命令 ACK 调度 | 状态变更路径相悖（ACK 非可靠送达） | command_revision=设备已应用高水位、每次窗口携带；backend 幂等翻转不依赖单次 ACK |

**Deferred 不应延后**：A-2（JSON/sync-contract 冻结，耦合发散对 1、2、4）与 A-1（通道选型，耦合发散对 3）应在相应两个单元各自 spec 前收敛；spine 与 .memlog 对 A-1 的矛盾（待定 vs 已定 WebSocket）需先修复。
