## Story

As a 设备用户，
I want 同一批离线数据重复提交也只被确认一次，
So that 网络重试不会制造重复敲击。

**覆盖需求：** FR-C-007、AD-3、NFR4

## Acceptance Criteria

1. **高于确认值的差量只确认一次（FR-C-007 / AD-3）**
   **Given** mock device 以 JWT 身份提交契约 §6.1 上报必填字段（含 `local_total`、`acked_total`、轮次、游标、状态、`applied_revision`、设备状态镜像与 `action_id`）
   **When** backend 处理高水位
   **Then** 仅当请求 `local_total` **高于** cloud 已确认 `acked_total` 时，把权威 `acked_total` 幂等推进到该 `local_total`（差量只确认一次）
   **And** 同值或更低（`local_total ≤ cloud.acked_total` 且不构成设备重置冲突）为**幂等 no-op**（HTTP 200 + `code=0`），不增加计数、不改权威高水位
   **And** 响应复用 Story 4.6 的 `StateSnapshotResponse`（17 字段闭包），差量 = 响应 `acked_total` − 请求 `acked_total`（派生量，**不得**新增 `delta`/`high_watermark` wire 字段）
   **And** 响应携带确认后的轮次状态（`round_id`/`round_state`/`round_cursor`/`pending_completion`）、待应用命令载荷（`command_revision`/`volume`/`brightness`/`timeout`）与可对账字段（含导出的 `snapshot_seq`）

2. **冲突返回明确业务错误与可恢复基准（FR-C-007 / §8 / §12）**
   **Given** 设备身份、轮次边界、基准高水位、经文版本或设备重置冲突
   **When** backend 校验提交
   **Then** 返回 HTTP 200 + 契约 §12 已冻结业务码，**不**盲推游标、**不**静默回退权威高水位、**不**无限重试
   **And** 业务拒绝响应必须经 `ApiResponse.error(int, String, T)` 携带**完整权威快照**（§12；不得只回 `{code,message}`）
   **And** 选码以契约 `condition` 文案为唯一依据，**不得**新增/删除/改义任何 `ErrorCode` 常量：
     - 轮次无法归属 → `20001 ROUND_UNASSIGNED`
     - 缺少可验证基准高水位 → `20002 BASELINE_HIGH_WATER_MISSING`
     - 设备重置（请求 `local_total` 低于 cloud 基准）→ `20003 DEVICE_RESET_CONFLICT`
     - 请求积压差（`local_total − acked_total`）**达到** 1000 → `20004 QUEUE_FULL`（**不阻断确认**：同一次响应仍按 §6.3 幂等推进并回传最新确认高水位）
     - `scripture_version` ≠ canonical `HS-1.0.0` → `20005 SCRIPTURE_VERSION_MISMATCH`（停止推进）
   **And** 请求体中的 `device_id` 一律不可信；身份只取 `UserContext.currentDeviceId()`；与落盘身份不匹配仍由既有过滤器回 `40300`

3. **Mock 覆盖重复、乱序、降低高水位与跨轮提交**
   **Given** 以 mock device / MockMvc 驱动同步写路径
   **When** 执行契约行为矩阵
   **Then** 至少覆盖：重复提交同值 no-op、乱序/重试同 `action_id` 返回同一结果、`local_total` 降低触发 `20003`、跨轮无法归属触发 `20001`、积压达上限 `20004` 仍确认、版本不一致 `20005` 不推进
   **And** 写路径遵守「先 `progress.json`（权威），再派生 `commands.json`/`device_state.json`」；派生写失败不回滚已确认权威（幂等重放会收敛）
   **And** **不得**写入 `daily_stats.json`（属 Story 5.3）、**不得**实现 WebSocket 推送（属 5.5）、**不得**实现完成锁定/从头开始/退出（属 5.2）、**不得**实现命令下发与修订递增（属 5.4）

### 必须作出的裁决（推荐项 + 约束证明；实现时必须在 javadoc 落地）

**裁决 A：高水位推进操作数**
- **推荐：权威推进条件为 `request.local_total > cloud.acked_total`，新权威 `acked_total := request.local_total`；同时把权威 `local_total` 更新为请求 `local_total`（cloud 镜像设备已报本地事实）。**
- `request.acked_total` 只作差量操作数与积压判定输入，**不得**被写成权威 `acked_total`。
- `local_total == cloud.acked_total` → 成功 no-op；`local_total < cloud.acked_total` → `20003`（§8 设备重置），响应携带 cloud 基准供设备重建。
- **首启 / `progress.json` 缺失**：cloud 侧视 `acked_total=0`、无已确认轮次（与 4.6 未初始化表达一致）；首次 `local_total > 0` 的合法上报创建权威文件，不得因「文件不存在」回 `50000` 或 `20002`。
- **不得**按「请求 `acked_total` 与 cloud 的差」推进（那会把客户端自报基准变成权威）。

**裁决 B：轮次确认边界（本 Story vs 5.2）**
- **推荐：校验取值域后，把请求的 `round_id`/`round_state`/`round_cursor`/`pending_completion` 写入权威事务组（与高水位同一次 `ProgressStore.write`）。**
- 取值域：`round_id ≥ 1`、`round_cursor ≥ 0` 且 `≤ consumableHan`、`round_state ∈ {in_progress,completed}`。
- **跨轮无法归属**：若 cloud 已有进行中轮次，而请求 `round_id` 小于权威 `round_id`，或在 `pending_completion==true` 时提交更大的新 `round_id` 试图覆盖未确认完成 → `20001`（详细分支写进 javadoc；不得盲推）。
- **明确不做（交给 5.2）**：完成确认清除 `pending_completion`、`action_id` 驱动的「从头开始/退出」、完成锁定期间拒绝正式输入的 cloud 侧状态机。本 Story 只做边界校验 + 确认落盘。

**裁决 C：`20004` 与确认同事务**
- **推荐：先算积压标志，再执行可执行的幂等推进，最后若积压达上限则以 `ApiResponse.error(20004, …, snapshot)` 返回（HTTP 200），snapshot 中的 `acked_total` 已是确认后值。**
- 若同时命中更严重的硬冲突（`20003`/`20005`/`20001`），硬冲突优先，**不推进**。
- 判定输入仅为请求字段差，阈值「≥ 1000」即达上限（与设备 Story 2.2 / 契约 §12 一致）。

**裁决 D：上报路径**
- **推荐：`POST /api/v1/sync/report`**，请求体 = §6.1 必填闭包。
- 理由：`/api/v1` 前缀已冻结；样例 id `https_sync_report`；与既有 `GET /api/v1/sync/snapshot` 同控制器、同路径族。
- **该路径未被契约冻结**（同 4.6 缺口 1）→ 登记 deferred，不得改契约。

**裁决 E：`scripture_version` 读取面**
- **推荐：启动或首次校验时从 classpath `canonical/heart-sutra.json` 读取 `scriptureVersion`，缓存为单一来源；比较请求字符串全等。**
