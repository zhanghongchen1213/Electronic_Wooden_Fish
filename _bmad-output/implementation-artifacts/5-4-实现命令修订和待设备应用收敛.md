## Story

As a 设备用户，
I want 离线修改设置后最终只应用最新版本，
So that 设备页不会把旧设置误报为已生效。

**覆盖需求：** FR-C-008、AD-5

## Acceptance Criteria

1. **只保留最新 `command_revision`，旧修订不可覆盖（FR-C-008 / AD-5 / §9）**
   **Given** 已鉴权身份（JWT → `UserContext.currentDeviceId()`）连续提交音量 / 亮度 / 熄屏设置命令（设置命令族）
   **When** backend 保存命令
   **Then** 每次**新** `action_id` 使权威 `command_revision` **单调 +1**，`commands.json` **只保留最新**载荷（`volume`/`brightness`/`timeout`）与该设置族 `action_id`；旧修订字节不得写回覆盖新修订
   **And** 同设置族 `action_id` 重放返回与首次成功一致的权威快照（幂等；不二次递增修订）
   **And** 若请求携带乐观并发基线 `base_revision` 且与当前 `command_revision` 不一致 → HTTP 200 + 业务码 `20006 COMMAND_STALE_REVISION`，**不改盘**，拒绝响应经 `ApiResponse.error(int,String,T)` 携带**完整 17 字段快照**
   **And** 响应复用 `StateSnapshotResponse`（17 字段闭包）；命令维度「待设备应用 / 已生效」**不是** wire 字段——客户端（及本 Story 测试）按契约 §5.2 / §9 用 `applied_revision ≥ command_revision` 派生（`StateSnapshotService.commandApplied`）
   **And** 篇章动作族（restart/exit）已由 Story 5.2 落地；「立即同步」仍不在本 Story（见明确不做）

2. **活动窗口回传后幂等收敛为已生效（FR-C-008 / AD-5）**
   **Given** 设置命令已落盘且 `command_revision > applied_revision`（待设备应用）
   **When** mock device 经既有 `POST /api/v1/sync/report` 回传 `applied_revision`，且 `applied_revision ≥ command_revision`
   **Then** backend **不依赖单次 ACK 到达**：只要回传高水位满足判定，快照派生为「已生效」；重复 report / 重复获取命令不改变最终载荷与修订号对
   **And** report 路径继续遵守 5.1 裁决 F：`applied_revision` **单调不减**；**不得**因 report 递增 `command_revision` 或改写设置载荷
   **And** 连续提交更新修订后，旧 `applied_revision` 在未追上前保持「待设备应用」；不得把未追上的状态呈现为已生效

3. **门禁、边界与不变量（NFR4 / AD-16）**
   **Given** 设置下发与高水位 report / 篇章动作交叉执行
   **When** mock 驱动写路径
   **Then** 与 `ProgressSyncService` **共用同一 `deviceId` 互斥锁**，禁止 commands 与 progress 交错撕裂
   **And** 写序：设置下发只写 `commands.json`（本路径**不**改 `progress.json` / `daily_stats.json` / `device_state.json`）；report 写序仍为 progress → daily_stats → commands → device_state
   **And** 不得改 `docs/contracts/**` 字节；不得新增/删除/改义 `ErrorCode` 常量（本 Story **首次真实抛出**已预留的 `20006`）；不得把 `pending_apply`/`applied` 塞进 17 字段快照；不得新增第六个状态文件或数据库

### 必须作出的裁决（推荐项；实现须写入 javadoc）

**裁决 A：路径**
- **推荐：`POST /api/v1/sync/command`**
- 理由：与 `/report`、`/round-action`、`/stats` 同控制器族；语义是「下发设置命令」而非篇章动作；契约未冻结 REST 路径 → deferred。
- 身份：`UserContext.currentDeviceId()`；无 path/query device_id。

**裁决 B：请求体字段**
- **推荐 wire（snake_case）：** `volume`（int）、`brightness`（string）、`timeout`（int）、`action_id`（string）、`base_revision`（Integer，**可选**）。
- `base_revision` 为 REST 乐观并发基线（契约未列）→ deferred；缺省表示「无 CAS，LWW 递增」。
- **禁止**客户端提交 `command_revision` / `applied_revision` 作为权威写入值。

**裁决 C：修订递增与只留最新**
- **推荐：** 文件缺失视为 `command_revision=0`、`applied_revision=0`、载荷=§9.1 默认；新 `action_id` → `command_revision += 1` 并整体替换六字段；旧修订不得以更低修订号写回。
- 同 `action_id` → 纯读返回，不写盘（或写盘亦不变，测试以观测值为准）。

**裁决 D：`20006` 触发**
- **推荐：** （1）`base_revision != null && base_revision != current_command_revision`；（2）任何将写入的 `command_revision` 严格小于磁盘当前值的防御分支。
- 拒绝时 **不改盘**，HTTP 200 + `20006` + 完整快照。
- 同值高水位 report、同 action_id 重放 **不是** `20006`。

**裁决 E：与 report 的收敛**
- **推荐：** 不新增 ACK 端点；收敛唯一输入仍是 report 的 `applied_revision`（5.1 已实现单调不减镜像）。本 Story 补的是「先抬 command_revision，再等 applied 追上」。
- 测试必须覆盖：submit → pending → report 追上 → applied；以及 submit→submit→report 只认最新载荷。

**裁决 F：锁与服务边界**
- **推荐：** 设置下发入口放在 `ProgressSyncService`（或抽取共享 `DeviceMutex` bean 供两服务注入——若抽取，须单例且键为 deviceId）。**禁止**第二套 `ConcurrentHashMap` 锁导致与 report 竞态。
- 设置下发 **不**调用 `HistoryStatsService`、**不**写 device_state。

## Architecture Compliance

- **AD-2**：命令状态权威在 backend；小程序只呈现已确认/已派生状态。
- **AD-5**：`command_revision` 单调递增只留最新；`applied_revision` 独立高水位；`≥` 判定翻转为已生效；不依赖单次 ACK。
- **AD-16**：零库；`commands.json` 原子整体替换。
- **Consistency Conventions**：命令「待设备应用」是独立维度，不得并入五值累计同步词表。
- **NFR4 / SM-4**：重复获取/回传/乱序最终只保留最新设置且不误报已生效。

## Library / Framework Requirements

- Java 17、Spring Boot 3.3.7；**不新增运行时依赖**。
- `@Valid @RequestBody` → `MethodArgumentNotValidException` → 既有 `40000`（Spring Framework 6.1 Validation；与 5.1/5.2 相同，避免在 `@RequestBody` 上叠方法级约束导致异常类型漂移）。参考：https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-validation.html
- 取值域可用 `@Min`/`@Max`/`@Pattern`/`@NotBlank`；`timeout` 推荐 `@Pattern` 或自定义校验映射到 {5,15,30}（若用 int + 服务内校验，须统一错误体为 `40000`）。
