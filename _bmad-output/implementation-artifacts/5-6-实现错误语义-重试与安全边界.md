## Story

As a 小程序用户，
I want 同步失败和协议错误有清晰、可重试的结果，
so that 我不会把失败误解成已成功。

**覆盖需求：** FR-C-011、AD-16、AD-18

本 Story 是 Epic 5 对 FR-C-011 的**业务接口验收与客户端重试边界闭合**：Story 4.3/4.4 已建立信封、
`ErrorCode`、`GlobalExceptionHandler`、JWT 与敏感日志基线；5.1–5.5 已在各写路径返回契约拒绝码。
本 Story **不重造信封**，而是：(1) 把既有错误路径验收为「统一信封 + 可执行动作文案 + 不泄密」；
(2) 在 `cloud/frontend` 落地统一 `api/request` 与 **401 单飞刷新队列**（epics AC2 明确要求；
覆盖 4.4「留给 Epic 6」的临时分工——Epic 6.1/6.2 消费本层，不得再发明第二套 request）。

## Acceptance Criteria

1. **统一信封与可执行失败语义（FR-C-011 / AD-16 / 契约 §12）**
   **Given** 请求发生参数错误、身份错误、业务冲突、上游超时或服务器异常
   **When** `GlobalExceptionHandler` / `AuthFailureWriter` / 同步控制器拒绝分支处理异常或拒绝
   **Then** 始终返回 `{code,message[,data]}` 信封：成功 `code=0`；业务错误 HTTP 200 + `2xxxx`；
   协议/鉴权错误使用对应 HTTP 状态（`400xx`/`401xx`/`403xx`/`404xx`/`405xx`/`415xx`/`500xx`/`502xx`）
   **And** 业务错误**不得**伪装成 `code=0` 成功数据；`2xxxx` 同步拒绝仍经 `ApiResponse.error(int,String,T)`
   携带完整 17 字段快照（§12），供客户端重建基准而非无限重试
   **And** 失败 `message` 必须含可执行动作语义（「重试 / 重新登录 / 按本次响应重建本地基准 /
   继续上报收敛 / 修复后重试」之一），且**不得**把 `session_key`、JWT 明文、`Authorization`、
   AppSecret、原始 openid、异常栈或微信响应原文透出给客户端或写入普通日志

2. **Frontend 401 单飞刷新与安全边界（FR-C-011 / AD-18 / cloud/AGENTS.md §4）**
   **Given** frontend 同时收到多个 HTTP 401（或本地 access 提前过期）且 `requireAuth=true`
   **When** 令牌刷新成功或失败
   **Then** 全仓只经统一 `api/request` 出口；并发只发起**一次** `POST /auth/refresh`；等待者全部被唤醒
   （失败时 `cb(null)`，禁止永久挂起）；刷新成功后每个原请求**最多重试一次**；仍失败则
   `clearTokens` + **只跳转一次**登录入口（`uni.reLaunch` + 栈顶判重）
   **And** 本地持久化只允许 access/refresh/`expireTime`（及后续 Epic 6 的非权威 UI 缓存）；
   **绝不**持久化或日志打印 `session_key`、JWT 以外的微信会话材料；日志/toast 不得回显 token 明文

3. **门禁与范围边界**
   **Given** Epic 5 既有 REST/WS 与契约门禁
   **When** 完成本 Story
   **Then** `cd cloud/backend && mvn -q test`、frontend request 单测、`python3 docs/contracts/tests/run_sync_contract_tests.py`、
   `git diff --check` 全绿
   **And** 不得改 `docs/contracts/**` 字节；不得新增/改义 `ErrorCode`；不得引入 RFC 9457 Problem Details
   或第二套错误体；不得引入数据库；不得实现 MINI-06 页面视觉对拍（属 Epic 6）；不得改 Embedded

**关键真源结论**

1. **本 Story 是 FR-C-011 在 Epic 5 的验收门 + frontend 重试安全边界，不是第三套错误协议。**
2. **业务错误 ≠ HTTP 成功数据。** `code=0` 仅表示成功；`HTTP 200 + 2xxxx` 是业务拒绝，客户端必须当失败处理。
3. **可执行语义优先落在 `message` 与客户端码表，不扩展信封字段。** 禁止发明 `retryable: true` wire 字段（会破坏契约与既有测试）。
4. **401 单飞是正确性不变量，不是优化。** 失败不唤醒 = 永久挂起；每请求各刷 = 雪崩。
5. **禁止 RFC 9457 Problem Details。** Spring Boot 3.3 文档默认推 ProblemDetail；EWF 唯一形状是 `{code,message,data}`。
6. **不得新增 `ErrorCode`。** `20002 BASELINE_HIGH_WATER_MISSING` 若仍无写路径，保持登记但不强行发明触发条件。
7. **WS 通道不是 REST 信封。** 5.5 已定；本 Story 只加固 WS 鉴权失败日志脱敏，不把 REST 信封塞进 WS。

**裁决 A：范围切分**
- **推荐：Backend = 验收硬化 + 矩阵测试；Frontend = request/单飞/storage；UI 壳与登录页视觉 = Epic 6。**

**裁决 B：客户端动作码表（不入库、不进 wire）**

| code | HTTP | 客户端动作 |
| --- | --- | --- |
| 0 | 200 | 成功 |
| 20001–20003, 20005–20006 | 200 | 按响应快照重建/停止推进；**禁止**盲重试抬水位 |
| 20004 | 200 | 提示队列满；**继续上报收敛**（不阻断确认） |
| 40000/40001 | 400 | 修参数后重试 |
| 40101/40102/40103 | 401 | 单飞刷新 → 仍失败则重新登录 |
| 40300 | 403 | 重新登录（身份不匹配，无换机） |
| 40400/40500/41500 | 对应 | 协议问题；不盲重试业务写 |
| 50000/50200 | 500/502 | 稍后重试；不把失败当成功 |

**裁决 C：可执行文案**
- **推荐：沿用既有中文短句风格；矩阵测试用关键词断言（重试|重新登录|重建|收敛|修复）。**
- 不把 Node ID、实现说明、HTTP 原文塞进 message。

**裁决 D：Frontend 工程最小集**
- **推荐：本 Story 可新增 `cloud/frontend/package.json`、`tsconfig`、`vitest`、`src/api/*`、`src/utils/*`、`src/types/api.ts`。**
- **不做**完整 `pages.json` 四页导航与 Pen 对拍（6.1）；登录页文件可缺省，但 `redirectToLogin` 常量路径必须稳定为 `/pages/login/index`。
- uni API 通过注入/adapter 隔离，便于 Node 单测。

**裁决 E：单飞与重试次数**
- **推荐：刷新成功后 `return request(options)` 恰好一次；用 `options._retry` 或等价标志防回路。**
- refresh 请求本身 `requireAuth:false`，失败不得再触发刷新。

**裁决 F：敏感材料**
- **推荐：storage 白名单键 + 日志红队字符串扫描；JWT 只存字符串不 parse 后打日志。**

**裁决 G：与 Spring Problem Details 的关系**
- **推荐：显式关闭/不启用 `spring.mvc.problemdetails.enabled`；Handler 继续返回 `ApiResponse`。**
- 文档：https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html
