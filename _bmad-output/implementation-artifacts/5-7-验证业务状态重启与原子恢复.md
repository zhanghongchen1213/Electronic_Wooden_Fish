## Story

As a 设备用户,
I want 同步、完成、命令和统计在 backend 重启后仍然一致,
so that 服务维护不会破坏诵读。

**覆盖需求：** FR-C-010、FR-C-011、NFR4、NFR5

本 Story 是 Epic 5 的**业务状态重启与原子恢复验收门**：Story 4.5 已建立 `AtomicJsonFile` /
`PersistenceRecovery` 与「等价重启」Store 读回；5.1–5.6 已在写路径落盘高水位、轮次/完成、
日统计、命令修订、WS 推送与错误语义。本 Story **不重造持久化基元、不新增第六状态文件、
不改契约字节**，而是把「业务写路径 → 落盘 →（模拟）进程重启 → 读回/再处理」闭合为可失败的
验收证据，证明 SM-5 / NFR5 与 epics AC 在 **5.x 业务态**下成立。

## Acceptance Criteria

1. **重启后业务状态不互相矛盾（FR-C-010 / NFR5 / SM-5）**
   **Given** mock device 经既有写路径完成高水位 report、轮次完成/跨轮动作、设置命令与日统计更新，
   且权威文件已落盘；随后在写路径执行过程中或之后**停止**业务处理（测试用「重建服务/Store 实例
   + 同一 `app.data-dir`」模拟进程重启；见裁决 B）
   **When** 新实例启动并执行 `PersistenceRecovery.recover()`，再经 `ProgressSyncService` /
   `StateSnapshotService` / `HistoryStatsService` 读回
   **Then** `progress.json` 内 `local_total`/`acked_total`/`round_id`/`round_cursor`/`round_state`/
   `pending_completion`（及篇章 `action_id`）自洽且与快照 17 字段一致；`commands.json` 的
   `command_revision`/`applied_revision`/载荷与「待设备应用/已生效」派生一致；`daily_stats.json`
   桶合计不得大于权威 `acked_total`；`device_state.json`/`identity.json` 可读且不改写高水位
   **And** 目录中存在结构合法但数值不同的孤儿 `.progress-*.tmp`（或同类契约临时前缀）时：
   读取与恢复**只认精确文件名**，半写临时文件**不得**覆盖最后一个完整快照；恢复后 orphans
   被 best-effort 清理（清理失败只 WARN，权威字节不变）

2. **重启后最后一次请求保持幂等（FR-C-011 / NFR4 / SM-4）**
   **Given** 重启前最后一次成功请求（report / round-action / settings command）的请求体已保存为
   验收输入
   **When** 重启后 mock device **原样重放**该请求
   **Then** 不重复增加差量、不二次递增 `command_revision`、不创建第二个新 `round_id`（同
   `action_id` 短路径）；响应 `code=0` 且权威快照与重启前最终态一致（或与契约幂等 no-op 语义一致）
   **And** 恢复测试必须保存**输入、输出与文件校验**作为验收证据（见裁决 F）：至少包含请求 JSON、
   响应信封关键字段、五份契约文件的摘要/关键字段读回；证据路径写入 Completion Notes / 测试日志

3. **门禁与范围边界**
   **Given** Epic 5 既有 REST/WS 与契约门禁
   **When** 完成本 Story
   **Then** `cd cloud/backend && mvn -q test`、`python3 docs/contracts/tests/run_sync_contract_tests.py`、
   `git diff --check` 全绿；既有 `AtomicJsonFileTest` / `PersistenceRecoveryTest` / 5.1–5.6 契约测
   不回归
   **And** 不得改 `docs/contracts/**` 字节；不得新增/改义 `ErrorCode`；不得引入数据库或第六状态
   文件；不得改 `cloud/frontend/**`、`Embedded/**`；不得声称掉电安全或多进程文件锁已证明

### 必须作出的裁决（推荐项；实现须写入注释）

**裁决 A：范围切分**
- **推荐：验证优先 + 缺口才最小硬化；禁止重写 Store/基元/契约。**
- 理由：epics 标题为「验证」；4.5/5.x 已交付实现面。

**裁决 B：重启模拟手法**
- **推荐：同一 `@TempDir` data-dir 上销毁并重建 `ProgressSyncService` + 各 Store + 调用 `PersistenceRecovery.recover()`。**
- 可选增强：`@SpringBootTest` + `@DirtiesContext` 或第二上下文读同一目录——若成本高则不做，并记未证明面。
- **禁止**把「只调用 `store.read()` 而不重建服务」当作本 Story 唯一证据（那是 4.5 已覆盖面）。

**裁决 C：半写/崩溃注入**
- **推荐：权威文件保持最终完整字节；另写冲突数值的 `.progress-<rand>.tmp`（及可选 commands 临时前缀）。**
- 断言读取与快照仍为权威；恢复后 orphan 清理；**禁止**用 `Files.writeString(progress.json, partial)` 伪装原子写成功路径（那会破坏「完整快照」前提，除非单独测 fail-closed 损坏→50000）。

**裁决 D：业务剧本最小集**
- **推荐一条主剧本覆盖四类状态：** (1) report 抬 `acked_total` 并归档日统计；(2) 达末字完成；(3) `restart` 新 `round_id`；(4) settings 抬 `command_revision` 后再 report 收敛 `applied_revision`。
- 不要求穷尽 5.1–5.6 全部负例矩阵（那些已有契约测）。

**裁决 E：篇章动作跨重启幂等**
- **推荐：验收「最后一次 round-action」时，确保其 `action_id` 仍等于落盘 `progress.action_id`（之后无 report 覆盖该槽）。**
- 若测试先 restart 再 report，单槽被覆盖后，旧 restart 键跨重启**不**保证幂等——属 5.2 deferred，登记缺口，不在本 Story「修复」为持久化集合。

**裁决 F：验收证据**

- Completion Notes 列出绝对或 `/tmp` 日志路径；**禁止**提交证据到 git 跟踪的 `cloud/backend/data/`。

**裁决 G：与 FR-C-011 的关系**
