## Story

As a 设备用户，
I want 今日、近 7 日、近 30 日、累计和连续天数基于已确认数据计算，
So that 离线补传不会被错误归档。

**覆盖需求：** FR-C-005、AD-6、NFR4

## Acceptance Criteria

1. **确认差量按配置时区归档（FR-C-005 / AD-6）**
   **Given** mock device 经 JWT 身份上报，backend 按 Story 5.1 规则确认了高于权威的 `local_total` 差量（含离线积压一次补传）
   **When** 写路径按配置时区（`Asia/Shanghai`）以**确认时刻**归档
   **Then** 差量只累加进确认日对应的按日桶；今日 / 近 7 日 / 近 30 日 / 累计 / 连续天数**只**使用已确认敲击
   **And** 归档**不得**使用设备本地时钟、请求体中的任何日期字段（契约 §6.1 本无日期字段，禁止发明）或伪造「今天有敲击」的空记录
   **And** 同 `action_id` 重放、同值高水位 no-op **不得**二次累加日桶；`restart`/`exit` **不得**清零或改写日统计与 `acked_total`
   **And** 设备侧「未校时 / 待校时」语义（契约 §5.3 `untrusted_time`）由设备 UI Story 承担；本 Story 在 cloud 侧以「只用确认时刻、不接收设备日期」落实「不生成虚假当天记录」

2. **查询返回空态 / 待同步，且正式数字不含未确认差（FR-C-005 / AD-2 / UX-DR21）**
   **Given** frontend（或 mock）查询历史统计，且权威无任何已确认敲击，或 `progress.local_total > progress.acked_total`（云端已知待同步镜像）
   **When** 处理统计查询
   **Then** 响应携带明确空态与/或待同步标志；正式计数字段（今日/近7/近30/累计/连续）**不得**把未确认差值算入
   **And** 无历史时数字为 0 且空态为真，不得把「全 0」伪装成「有记录的成功日」
   **And** 同一权威落盘在进程重启后、重复查询后，统计结果保持稳定（NFR5 / SM-5 对历史统计的可恢复性）

3. **幂等、写序与门禁（NFR4 / AD-16）**
   **Given** 确认推进与查询在 mock 下交叉执行
   **When** 重复确认、跨越日界（注入 `Clock`）、损坏/缺失 `daily_stats.json`、派生写失败
   **Then** 权威 `progress.json` 仍先写后确认；`daily_stats.json` 为派生面——写失败**不回滚**已确认高水位，但必须可通过「`acked_total` 与桶合计差」在后续写路径 catch-up 收敛（见裁决 E）
   **And** 不得改 `docs/contracts/**` 字节；`DailyStatsStore.allowedFields()` 仍返回空集以匹配契约 §11「字段列 = 无」；桶形状只作为实现冻结（登记 deferred）
   **And** 不得把统计字段塞进 17 字段 `StateSnapshotResponse`；不得新增 `ErrorCode` 常量

### 必须作出的裁决（推荐项；实现须写入 javadoc）

**裁决 A：归档触发与时间源**
- **推荐：** 仅当权威 `acked_total` 相对「上次成功收敛的桶合计」增大时，把差值 `delta` 全部记入 `LocalDate.now(clock)`（zone=`Asia/Shanghai`）对应桶的 `confirmed_taps`。
- 时间源唯一：注入的 `Clock`（生产 `Clock.system(ZoneId.of("Asia/Shanghai"))`）。测试用 `Clock.fixed` / 可拨动实现。
- **禁止**读取请求日期、设备固件时间、或 `ZoneId.systemDefault()`。

**裁决 B：桶 JSON 形状（实现冻结，非契约字段）**
- **推荐：**
  ```json
  {"schema_version":1,"buckets":{"2026-09-23":{"confirmed_taps":12}}}
  ```
- 键：严格 `yyyy-MM-dd`（上海自然日）。值：仅 `confirmed_taps`（int ≥ 0）。无敲击的日期**不**写 0 桶（缺失即 0）。
- `DailyStatsStore.allowedFields()` 继续 `Set.of()`。

**裁决 C：查询响应字段**
- **推荐 wire（snake_case）：** `today_taps`、`last_7_days_taps`、`last_30_days_taps`、`total_taps`、`streak_days`、`empty`、`pending_sync`。
- 窗口：`last_7` / `last_30` 含今日共 7/30 个上海自然日（今日往前）。
- `total_taps` := `acked_total`（与桶合计收敛后应一致；查询以 progress 为准，避免派生滞后时数字分裂）。
- 该 DTO **不在**契约注册表——登记 deferred（与 `/snapshot`、`/report` 同族 REST 缺口）。

**裁决 D：路径**
- **推荐：`GET /api/v1/sync/stats`**，无必填 query；身份取 `UserContext.currentDeviceId()`。
- 理由：与现有 sync 控制器族一致；记录页（6.6）只读消费；不污染 §6.1 上报闭包。

**裁决 E：派生失败与 catch-up**
- **推荐：** 不变量目标 `Σ confirmed_taps == acked_total`。每次写路径（含 no-op/`action_id` 短路径）在持有 `deviceLocks` 时：若 `acked_total > Σ`，把差额记入**当日**桶并写回；若 `Σ > acked_total` → `50000` fail closed（数据遭篡改，不静默砍桶）。
- 查询路径只读，发现不一致时**不**写盘（返回仍以 `acked_total` 为累计权威；周期窗口按桶只读求和——若滞后，今日可能暂时偏低，直到下次 sync catch-up；测试须覆盖「写失败→再 report→收敛」）。

**裁决 F：连续天数**
- **推荐：** 从「今日」起向过去逐日查看桶：若今日 `confirmed_taps==0`，则从昨日开始计（避免日界刚过、今日尚未敲击时把连续天清零）；连续有敲击的天数即 `streak_days`；若今日与昨日皆 0 → `0`。
- 理由：与「按已确认敲击存在性」一致，且符合日常「连续打卡」预期；须在测试中用固定 Clock 钉死日界两边。
