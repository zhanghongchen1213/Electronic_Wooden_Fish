## Story

As a Embedded/cloud 开发者，
I want 把字段、事件、序号和跨轮边界写入统一同步契约，
so that 并行实现可以使用同一协议而不各自猜测。

本 Story 覆盖 FR-C-003、FR-C-006、AD-2、AD-3、AD-5、AD-6、AD-19，是 Epic 4 的
**第二道门禁**。Story 4.1 已钉死「唯一经文」；本 Story 钉死「唯一协议」——在 backend
启动基线（4.3）、身份入口（4.4）、原子持久化（4.5）、快照恢复（4.6）以及 Epic 5 的
同步实现之前，把跨层字段、事件来源、轮次边界、序号与恢复语义一次性冻结为
**可引用、可测试、不在各层重复定义**的单一文本源。

本 Story 只产出契约与校验设施，**不写任何运行期代码**（无 Java / TypeScript / C），
不修改 `Embedded/`，不创建 `cloud/backend/pom.xml`，不实现同步、游标推进、命令应用、
WebSocket 服务或小程序页面。Epic 2/3（Embedded）与 Epic 5/6（cloud）共同消费本契约。

## Acceptance Criteria

1. **Given** `docs/contracts/sync-contract.md` 当前只有 README 占位，
   **When** 创建契约正文，
   **Then** 定义 `device_id`、高水位、轮次、状态、命令修订、设备状态、`snapshot_seq`、
   `replay_cursor` 和 `action_id`，
   **And** 明确 `physical_pvdf`、`device_touch`、`automatic_tap` 三类来源及累计/轮次/完成语义。

2. **Given** 设备离线、完成未确认、设备重置、WebSocket 空洞或命令重复，
   **When** 契约描述恢复和错误路径，
   **Then** 明确按 `round_id` 分段、`pending_completion`、冲突恢复、快照水位续订、
   幂等重放和拒绝条件，
   **And** WebSocket 帧、心跳和重连参数留有可测试的版本化字段，不在各层重复定义。

3. **Given** 契约正文已定义字段与语义，
   **When** 执行契约门禁，
   **Then** 机器可读注册表覆盖 PRD §7 全部统一字段、事件来源枚举恰为三类、状态词表与既冻结口径一致，
   **And** 门禁在字段缺失、枚举未收敛、md 与注册表双真源或参数越界时以非 0 退出码失败，
   负例在临时副本上执行且不污染交付物。

4. **And** 契约不自行定义 `scripture_version` 的取值，只引用 canonical manifest；
   不把经文长度（260/303）或设备 7 槽 / 设备 13 槽 / 小程序 17 槽当成上限写入任何字段约束。

5. **Given** 契约已冻结，
   **When** 检查仓库内引用跨层契约的文档，
   **Then** `docs/contracts/README.md` 与 `docs/README.md` 不再声称契约「尚未创建」或「待冻结」，
   **And** 字段表、事件来源枚举与 WebSocket 参数只在契约中定义一次，其它文档只引用不复制。

6. **Given** PRD §13.1 Open Question 5 要求「`automatic_tap`、`round_id`、`pending_completion`、
   `action_id`、`snapshot_seq`、`replay_cursor` 必须在 `docs/contracts/sync-contract.md` 创建时
   一并冻结，并同步更新 `ARCHITECTURE-SPINE.md` 的正式输入枚举」，
   **When** 契约冻结，
   **Then** `ARCHITECTURE-SPINE.md` 的正式输入枚举收敛为三类、同步字段清单补齐
   `pending_completion` / `snapshot_seq` / `replay_cursor` / `action_id`，
   **And** AD-1（旧「仅有两类正式输入」）与 AD-5（把 `command_revision` 单一地描述为
   已应用高水位）的措辞与新枚举不再自相矛盾。

已核实的冲突与空白（本 Story 必须按下列裁决执行，不得来回摇摆）：

1. **契约文件当前不存在。** 已核实：`docs/contracts/` 下只有 `README.md`（占位，声明
   `sync-contract.md` 尚未创建）与 `canonical/`（Story 4.1 交付）。故本 Story 新建
   `docs/contracts/sync-contract.md` 及其配套注册表与门禁，并**必须**同步改写占位说明
   （AC 5），否则仓库会同时存在「已冻结契约」与「尚未创建」两种事实。
2. **正式输入枚举冲突（AD-1 vs PRD）。** `ARCHITECTURE-SPINE.md` AD-1 与
   §Structural Seed 的「事件来源」只列 `physical_pvdf`、`device_touch` 两类；
   `prd.md` §4 术语表与 §7 明确第三类 `automatic_tap`（该事件由 Embedded 内部生成、
   按真实敲击相同路径处理、数量并入 `local_total`/`acked_total`、**不新增独立 cloud 字段**）。
   `epics.md` AD-1 亦写明「架构旧文案将正式输入写成两类，需由同步契约按 PRD 最终枚举收敛」。
   → **裁决：枚举取三类**（产品行为 PRD 高于架构不变量），并按 AC 6 同步更新 spine。
3. **`command_revision` 语义分层冲突（AD-5 vs PRD §7）。** spine AD-5 把
   `command_revision` 单一地定义为「设备已应用命令的单调高水位」；`prd.md` §7 区分
   `command_revision`（命令修订）与 `applied_revision`（设备已应用），并规定
   「只有 `applied_revision == current_revision` 才显示已生效」。`epics.md` AD-5 也要求
   设备「回传已应用高水位」。→ **裁决：字段分两层**——`command_revision` 为 backend
   已下发的最新修订（单调递增），`applied_revision` 为设备已应用高水位（单调不减），
   已生效判定为 `applied_revision >= command_revision`。该裁决同时满足 PRD、epics 与
   spine AD-5 的意图（AD-5 的「不依赖单次 ACK 到达」正是靠回传高水位实现），
   并按 AC 6 把 spine AD-5 措辞改为分层表述。
4. **「待设备应用」不是累计同步状态。** PRD §7 与 spine §Consistency Conventions 均要求
   命令维度独立。→ 契约中**分成两个枚举**，不得并入同一枚举（负例 6）。
5. **JSON schema 与文件粒度仍在架构 Deferred（`[ASSUMPTION A-2]`）**，其闭合条件即
   「经 `docs/contracts/sync-contract.md` 收敛」。→ 本 Story 冻结**形状**（文件清单、
   承载事实、schema_version、迁移说明）与**单事务分组约束**，不实现原子写（属 4.5）。
6. **WebSocket 帧/心跳/重连参数属架构 Deferred**（通道已定为 WebSocket，参数下沉契约）。
   → 本 Story 冻结参数默认值与可测试上界，并显式记录「生产反代空闲超时未冻结」
   属部署阶段 Deferred，参数可经 `contract_version` 递增演进。
7. **槽位不是长度。** 设备 7 槽、设备经文页每行 13 槽、小程序每行 17 槽都是视口槽位；
   经文长度唯一来源是 canonical manifest 的 `counts.consumable_han`。→ 契约与注册表
   **不得**出现槽位常量或经文长度字面量作为任何字段的上界（AC 4、负例 8）。
8. **`local_total` 必须与轮次字段同事务落盘。** PRD §7 末条要求 `local_total`、
   `acked_total`、`round_id`、`round_cursor`、`round_state`、`pending_completion`
   及相关 `action_id` 作为**同一持久化事务**提交。→ 契约必须把这组字段约束在同一个
   持久化文件内（原子 `rename` 即事务边界），不得分散到多个文件。

### 事件来源与累计语义（AC 1）

- 枚举**恰为** `physical_pvdf`、`device_touch`、`automatic_tap`。
- 三类进入**同一个**有效敲击队列，共享本地累计、经文推进、完成锁定、音频、RGB、
  持久化与同步结果；除该队列外任何路径不得推进正式累计。
- `automatic_tap` 由 Embedded 定时器生成（3 秒周期锚点），按真实敲击相同路径处理；
  **其数量并入 `local_total`/`acked_total`，不新增独立 cloud 累计字段或同步接口**；
  自动模式只存在于内存、不跨重启持久化。
- 不计数的边界：熄屏首次触摸只唤醒；充电中、完成遮罩中、故障锁定中忽略输入。
- 一次有效敲击只推进一个**可消费汉字**；标点/空格/换行随紧邻前一个汉字在同一步内出现，
  不消耗敲击、不单独推进游标（消费语义已由 Story 4.1 固定，契约只引用，不重定义）。

### 状态词表（AC 1）

- **累计同步状态（5 值，互斥）**：本地已记录 / 同步中 / 已同步 / 待同步 / 同步失败。
- **命令维度（2 值，独立）**：待设备应用 / 已生效。
- **可信时间门禁**：待校时（无可信日期时设备今日显示该状态，cloud 不伪造当天统计）。
- 契约必须给出 wire 名（全小写下划线，与 spine §Consistency Conventions 一致）与
  冻结中文显示词的映射；命令维度**不得**并入累计同步状态枚举。

### 轮次、完成与跨轮竞态（AC 2）

- 离线差量按 `round_id` 分段提交；无法归属轮次或缺少基准高水位时**拒绝确认**，
  不把一个累计高水位盲推到新轮次。
- 设备本地到达末字而 cloud 未确认 → `pending_completion`；完成确认前不得创建新轮次。
- 「从头开始」使用幂等 `action_id`，重复请求返回**同一** `round_id`。
- 离线「完成→从头开始」竞态（架构 Deferred 明确要求在本契约冻结）必须给出裁决：
  设备在未获完成确认时提交新 `round_id` 时，backend 的归属规则、被确认的完成是否
  仍归属旧 `round_id`、以及设备端本地重置与 cloud 基准的收敛顺序。裁决必须与
  AD-3「单轮推进只在设备本地发生、backend 只做边界校验与确认」一致。
- 「退出」保留完成状态与历史统计；新轮次不清除旧篇章和累计。

### 恢复与冲突路径（AC 2）

| 场景 | 契约必须给出的语义 |
| --- | --- |
| 设备离线后补传 | 按 `round_id` 分段；高于 `acked_total` 的差值只推进一次；同值/更低 no-op |
| 完成未确认 | `pending_completion` 置位；不得提前进入完成态；不得创建新轮次 |
| 设备重置（`local_total` < cloud 基准） | 返回**可恢复的冲突状态**；禁止静默回退或无限重试；设备必须按 cloud 基准重建本地高水位后再继续 |
| 离线积压达上限（> 1000） | 统一拒绝新输入并提示；不得静默丢弃 |
| WebSocket 序号空洞 | 先查询补齐再续播；不消费空洞之后的序号 |
| 断线重连 | 以查询响应冻结的 `snapshot_seq` 为唯一基准，从 `snapshot_seq + 1` 续订；`seq <= last_applied_seq` 丢弃 |
| 小程序回放 | 持久化 `replay_cursor`；回放期间新事件排队；事件携带 `round_id`，旧轮次事件不得写入当前篇章 |
| 命令重复/乱序 | 旧修订不覆盖新修订；重复获取/回传幂等；设置命令与篇章动作的 `action_id` 不互相覆盖 |
| `scripture_version` 不一致 | 配置错误：停止推进并报告，不做自动映射、选经或导入 |

### 命令修订与 `action_id`（AC 1, 2）

- `command_revision` = backend 已下发的最新修订；`applied_revision` = 设备已应用高水位。
- 已生效判定：`applied_revision >= command_revision`；据此把「待设备应用」翻转为「已生效」，
  **不依赖单次 ACK 到达**（AD-5）。
- 设备应用命令时必须原子写入字段与 `applied_revision`。
- `action_id` 的幂等语义：同一 `action_id` 重复提交返回同一结果；新轮次动作重复提交
  返回同一 `round_id`。

### WebSocket 契约（AC 2）

**帧类型（每帧必带契约版本字段与判别字段）**：

| 帧 | 方向 | 内容 | 出处 |
| --- | --- | --- | --- |
| `snapshot` | backend → frontend | 权威快照 + `snapshot_seq` + 轮次 + 命令状态 + 设备状态 | FR-C-006 |
| `delta` | backend → frontend | 已确认差量，带单调 `seq` 与 `round_id` | FR-C-009 / AD-17 |
| `completion` | backend → frontend | 完成确认 | FR-C-016 |
| `command_state` | backend → frontend | 命令下发/已生效状态变化 | FR-C-008 |
| `heartbeat` / `heartbeat_ack` | frontend ↔ backend | 应用层心跳 | AD-17（参数下沉契约） |
| `error` | backend → frontend | 协议/权限错误 | FR-C-011 |

**Endpoint 派生规则（AD-20 强制）**：`VITE_API_BASE_URL` 是含 `/api/v1` 的 REST base，
WebSocket 的 origin/path **由本契约派生**，不在 env 中重复拼接：origin 取
`VITE_API_BASE_URL` 的同源（`https` → `wss`、`http` → `ws`），路径为 REST base 加固定
后缀；鉴权令牌**只经 query 参数**传递（小程序不支持自定义 header）。契约必须写明该派生
规则与 query 字段名，且不得写入具体域名或 AppID（属部署 Deferred）。

**心跳与重连参数（版本化 + 可测试）**：必须给出带单位的具体默认值与测试上界。可核验的
外部约束（本轮 web 复核）：

- 微信小程序网络请求默认与最大超时均为 **60 s**；小程序**不提供**自动 ping/pong 保活，
  也不提供自动重连，心跳与重连必须应用层实现；切后台/切页**不触发** `onClose`（静默断连），
  不能只依赖 `onClose` 判定失效；小程序同时最多 **5 个** WebSocket 连接（基础库 1.7.0+），
  故契约应约束「单一活跃 socket」。
  来源：[uni-app connectSocket 文档](https://en.uniapp.dcloud.io/api/request/websocket.html)、
  [uni-app WebSocket 多连接与心跳实践](https://blog.csdn.net/gray5/article/details/154222389)、
  [uni-app 心跳重连实战](https://www.php.cn/faq/2351895.html)、
  [腾讯云小程序网络文档](https://intl.cloud.tencent.com/zh/document/product/1219/61745)
- 浏览器/小程序 JS 无法观测协议级 ping/pong 控制帧，**应用层心跳是唯一可见机制**；
  生产级默认是服务端发起心跳、心跳间隔取最短代理空闲超时的 ~75%、缺失 pong 约 10 s 判死；
  TCP keepalive 默认 7200 s，对 WebSocket 无效。
  来源：[WebSocket Heartbeat 指南](https://websocket.org/guides/heartbeat/)
- 重连采用**指数退避 + 抖动（full jitter）并设上限**，避免网关重启时的惊群。
  来源：[实时通信设计手册](https://raw.githubusercontent.com/handbook-academy/engineering-handbook/refs/heads/main/content/hld/part-2-building-blocks/10-real-time-communication.md)
- 关闭码取值域依 RFC 6455 §7.4：`1000` 正常关闭、`1001` 服务端离开、
  `1006` 异常关闭（只记录不处理）、`1008` 策略违规；业务错误使用 `4000–4999` 私有段。
  来源：[RFC 6455 §7.4（经 heartbeat 指南转述）](https://websocket.org/guides/heartbeat/)

→ 契约须给出并让门禁可断言：心跳间隔、心跳超时、重连初始退避、退避上限、抖动策略、
最大重连次数、关闭码白名单、续订起点规则。**测试上界建议**：心跳间隔 ≤ 45 s
（≤ 60 s 小程序超时的 75%）、心跳超时 ≤ 15 s、退避上限 ≤ 30 s、心跳间隔与超时均为正整数且
带 `_ms` 单位。生产反向代理的空闲超时尚未冻结（属部署 Deferred），契约须注明参数可在
代理超时确定后经 `contract_version` 递增调整，**不得**把部署参数写死为已验证事实。

### 必须失败的负例（AC 2, 3, 4, 5, 6）
