## Story

As a 小程序或设备客户端，
I want 获取带快照水位的权威状态和差量，
So that 断线后能从确定位置继续而不是猜计数。

**覆盖需求：** FR-C-006、AD-2、AD-17

## Acceptance Criteria

1. **权威状态查询响应**
   **Given** backend 已有已确认状态与单调序号
   **When** 客户端调用状态查询
   **Then** 响应同时包含权威快照、差量、`snapshot_seq`、轮次状态和命令状态
   **And** 响应 `data` 的字段集合恰为契约 §6.2 响应必填 ∪ `snapshot` 帧 `payload_fields` 的并集（17 个字段，见 Dev Notes「响应字段闭包」），不得新增 `delta`、`scripture_version`、`action_id`、`replay_cursor`、`last_applied_seq` 等任何契约未授权的 wire 字段
   **And** 差量不是新字段：按契约 §6.2，差量 = 响应 `acked_total` − 请求携带的基线 `acked_total`

2. **冻结水位是唯一基准**
   **Given** 一次查询响应已经返回
   **When** 客户端持有该响应
   **Then** `snapshot_seq` 在该响应内冻结，是该次响应的唯一恢复基准；客户端必须以它而不是自身展示计数作为续订与回放起点（契约 §8「断线重连」：从 `snapshot_seq + 1` 续订）
   **And** `snapshot_seq` 由 backend 从**已持久化的权威状态**确定性地导出，不在 `app.data-dir` 下新增任何承载文件或字段（`snapshot_seq` 的持久化作用域是 frontend，见契约 §11.1）

3. **不接受客户端自报展示计数**
   **Given** 客户端在查询请求中提交了自身展示计数或任何自报基准
   **When** backend 校验该请求
   **Then** 这些值只被当作**未经核实的声明**用于比较，绝不写入、绝不改变任何权威字段（`acked_total`、`round_id`、`round_state`、`round_cursor`、`pending_completion`、`command_revision`、`applied_revision`）
   **And** 当请求未携带可验证基准、或所携基准与 backend 已确认基准无法协调时，返回 §12 已冻结业务码中的对应码，且**该次响应仍携带完整权威基准**（§12：业务拒绝不得只回 `{code,message}`），使客户端据此重建本地基准

4. **序号空洞先补齐**
   **Given** 客户端的基准落后于 backend 已确认水位，或客户端声明的序号水位高于 backend 已确认值（存在空洞或越前）
   **When** backend 生成响应
   **Then** 返回完整权威快照与冻结的 `snapshot_seq` 作为补齐基准，绝不返回一个会跳字的「局部差量」，也不消费空洞之后的位置
   **And** 本 Story 只交付查询侧补齐基准；WebSocket 续订、`seq` 帧空间与断线补齐流程属 Epic 5，本 Story 不得实现

5. **旧轮次不得写入当前轮次**
   **Given** 请求或响应涉及轮次归属
   **When** backend 组织响应或校验请求
   **Then** 轮次相关字段只取自 `progress.json` 的权威单事务组，响应明确携带 `round_id`，使客户端能按 `round_id` 路由而不是按到达顺序
   **And** 无法把请求归入当前已确认轮次时，返回 `20001`（轮次无法归属）而不是把一个累计高水位盲推到新轮次

**关键真源结论（必须先读懂再动手）**

1. **本 Story 的「恢复基准」是快照水位，不是持久化恢复报告。** FR-C-006 的「恢复基准」= 查询响应冻结的 `snapshot_seq`，即客户端断线后重新对齐的唯一基准。`PersistenceRecovery` 的 javadoc 虽留有「对外可观测属 4.6/Epic 5 且需先评审契约」一句话，但把 `PersistenceRecoveryReport` 暴露成接口既不是 FR-C-006 的要求，也需要先改契约；**本 Story 不做**，按「明确不做」处理。
2. **契约没有冻结任何 REST 查询路径。** §12 只冻结 `/api/v1` 前缀与 `{code,message,data}` 信封；§10.2 只派生 WebSocket 路径；注册表 `endpoint` 只有 `rest_base_env`/`rest_base_contains`/`scheme_map`/`path_suffix`/`token_transport`/`token_query_field`。仓库现有路径只有 `/`、`/api/v1/health`、`/api/v1/auth/login/wechat-mini`、`/api/v1/auth/refresh`。**路径由本 Story 裁决（裁决 B）**，并把「路径未被契约冻结」登记为契约缺口。
3. **没有名为 `delta` 的字段，也没有 `high_watermark` 字段。** §6.2 把差量定义为「响应 `acked_total` 与请求 `acked_total` 之差」——是一个派生量，不是 wire 字段；高水位由 `acked_total`（已确认）与 `applied_revision`（已应用）承载。**不得发明这两个名字。**
4. **`snapshot_seq`/`replay_cursor`/`last_applied_seq` 的持久化作用域是 `frontend`**（契约 §11.1），`persistence_scopes[backend].fields` **恰好不含** `snapshot_seq`。而 §13 的门禁断言「承载通道含持久化文件的字段必有落点」——`snapshot_seq` 的落点是 frontend 作用域。**结论：backend 不得把 `snapshot_seq` 落盘。** 这也是裁决 A 的强制前提。
5. **§2 的 `snapshot_seq` 类型是 `integer ≥ 0`，取值域措辞为「单调递增；在查询响应内冻结，是续订与回放的唯一基准」**；`acked_total` 的措辞是「单调不减」。两者差别见裁决 A 的张力登记。
6. **`ErrorCode.BASELINE_HIGH_WATER_MISSING = 20002`、`ROUND_UNASSIGNED = 20001`、`DEVICE_RESET_CONFLICT = 20003` 已经存在但全仓无抛出分支。** 本 Story 是它们的第一批真实使用点，选码必须以其契约 `condition` 文案为唯一依据（裁决 D）。
7. **Epic 4 没有设备上报写路径。** Story 5.1 才是「高水位幂等同步」的写路径。本 Story 的「已确认状态」在测试中由既有 Store 直接播种（`ProgressStore.write(...)`），生产中读取现有持久化状态。**不得实现任何推进 `acked_total`/轮次/游标的写路径。**

### 关键回归风险（逐条必须在实现时守住）

1. **`snapshot_seq` 落盘 = 破坏契约门禁。** `persistence_scopes[backend].fields` 不含 `snapshot_seq`，`PersistenceFileContractTest` 会红；`PersistenceRecovery` 的 `ContractFile` 列表也固定为五份。→ 必须导出而非存储（裁决 A）。
2. **`data` 不能在业务错误上出现 —— 与契约 §12 直接冲突。** `ApiResponse.error(int,String)` 把 `data` 硬编码为 `null`，类级 `NON_NULL` 会删掉该键；`EnvelopeContractTest` 又把「业务错误只有 code/message」钉死。而 §12 明文要求业务拒绝仍回传 §6.2 必填字段（「不得只回 `{code,message}`」）。→ 裁决 C 必须显式处理，**不得**用「只回 `{code,message}`」蒙混（那违反 §12），也**不得**改写 `EnvelopeContractTest` 的既有断言（那会解除门禁钉扎，4.4 端已经因此被 review 要求恢复）。
3. **启动期建目录会污染工作区。** `EnvelopeContractTest` 是全上下文测试且未覆盖 `app.data-dir`（使用默认 `./data`），任何在启动或请求路径上创建数据目录的实现都会在 `cloud/backend/` 下留下未跟踪的 `data/`。→ 查询路径严格只读。

## Latest Technical Information

- **Spring Boot 3.3.7 / Spring Framework 6.1**：`@RequestParam(required = false)` 与 `@Validated` 的校验失败仍由 `HandlerMethodValidationException` 走既有 400/`40000` 映射；不要在控制器内手写校验错误响应。来源：<https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-validation.html>。
- **Jackson `@JsonInclude(NON_NULL)` 的语义**：类级注解对 `null` 字段生效、会**删除键**而不是写 `null`；若裁决 C 需要「错误也带 data」，必须让 `data` 非空，而不是改注解（改注解会连带破坏 `EnvelopeContractTest` 的成功无 data 断言）。来源：<https://github.com/FasterXML/jackson-annotations/wiki/Jackson-Annotations>。
- **`Optional.empty()` 与「未初始化」**：4.5 已把「存在性不可判定」收敛为 fail-closed（只用 `Files.notExists` 判缺失）。本 Story 的读取面必须沿用同一口径——不得用 `Files.exists` 把不可 stat 的文件当「缺失」而静默回退到默认基准（那正是 AC3 禁止的静默回退）。来源：`cloud/backend/src/main/java/top/zhcmqtt/ewf/backend/common/persistence/VersionedJsonFile.java`.
- **单调序号与重启**：无持久化计数器时，跨重启的严格递增无法保证；工业界做法是让序号从持久化的权威水位派生（如 Kafka 的 offset 即提交位置），而不是额外维护一个易碎计数器。来源：<https://kafka.apache.org/documentation/#impl_offsettracking>、<https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html>。
